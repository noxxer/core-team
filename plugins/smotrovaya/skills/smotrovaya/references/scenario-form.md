# Форма сценария

Сценарий — путь пользования шагами. Не тест-кейс: он не утверждает «правильно», он
предъявляет «вот что видно».

## Шаг

Шаг — действие и снимок **после** него. Три обязательных поля подписи и два необязательных:

| Поле | Обязательно | Что значит |
|---|---|---|
| `screen` | да | смысловой экран продукта |
| `account` | да | чьими глазами снято |
| `state` | нет (умолчание — базовое состояние) | что с данными на этом экране |
| `note` | нет | зачем этот снимок в ленте |
| `newFlow` | нет | шаг начинает **новый поток** |

```
scn.step(page, { screen: 'analysis', state: 'interpreted', account: 'owner',
                 note: 'разбор с пороговыми значениями' }, async () => {
  await page.getByRole('link', { name: 'Разбор' }).click()
})
```

## Экран ⊥ состояние — правило, которое нарушают молча

**`screen` — смысловой ЭКРАН, а не момент сценария.** Состояние данных идёт в `state`, а не
в новый код экрана.

Нарушение накапливается незаметно и **завышает продукт**: замер — один экран получил девять
кодов (`people-list`, `people-with-child`, `people-one-child`, `people-two-children`,
`people-pending-adult`, `dashboard`, `dashboard-1-analysis`…), разбор — четыре, персональная
панель — три. Карта продукта показала **52 «экрана» вместо 32**.

Компенсировать слоем псевдонимов в просмотрщике можно (недеструктивно, с бейджем «объединено
N»), но это лечение симптома: правильная починка — привести коды в самих сценариях.

## Новый поток

`newFlow: true` ставится на первый шаг потока, начинающегося с нуля внутри того же сценария
(например, регистрация второго пользователя). Он делает две вещи: обнуляет базу сравнения
для гарда дублей и **не даёт карте вывести ложное ребро-шов** «конец потока А → начало
потока Б».

**Не путать с передачей между аккаунтами:** там поток продолжается другой ролью — маркер не
ставится, карта сама покрасит переход как передачу.

## Дешёвый сценарий и дорогой

| | Дешёвый | Дорогой |
|---|---|---|
| Состояние | засеяно готовым | идёт настоящим путём |
| Что проверяет | экраны и переходы | весь конвейер целиком |
| Цена прогона | секунды | минуты и деньги |
| Сколько таких | большинство | один-два на весь стенд |

**Дорогой сценарий называется в брифе явно** — он тратит внешние ресурсы и требует
предусловий (очередь, туннель для внешнего вызова, живые ключи). Предусловие, не
выполненное перед прогоном, даёт падение, которое выглядит дефектом кода и им не является:
**падение по внешнему условию обязано говорить об этом текстом**.

## Что сценарий не делает

- **Не проверяет регистрацию, если он не про регистрацию.** Вход сеется, иначе половина
  времени прогона уходит на повторение одних и тех же экранов, а внешние ограничения
  (лимиты на отправку кода) начинают ронять прогон случайным образом.
- **Не удаляет каталог снимков.** Там лежат снимки других сценариев.
- **Не правит исходники продукта.** Стенд смотрит, а не чинит.

## Прогрев перед прогоном

Dev-сборщики компилируют страницу при первом обращении, и этот заход не укладывается в
таймауты сценария. Прогрев главных адресов перед прогоном дешевле, чем поднятые таймауты:
поднятый таймаут **прячет настоящую медленность продукта**, а прогрев — нет.

**Замер:** сценарий лендинга падал 3 раза из 4 на холодном стенде и давал 4 из 4 на прогретом.

## Параллелизм прогона

Замер важнее умолчания. На восьми сценариях: 1 поток — 8,4 мин (113/129 шагов ок), 2 потока —
5,1 мин (117/129), **4 потока — 3,6 мин (117/129)**.

Параллельный прогон оказался **и быстрее, и точнее**: часть прежних сбоев была неустойчивостью
по таймауту, а не поломкой. Дальше наращивать нечего — 3,6 минуты есть длительность самого
долгого сценария, то есть прогон упёрся в критический путь.

**Ограничение «только один поток», если оно есть, обязано быть проверено.** В боевом случае
комментарий «один поток обязателен, потому что сервер одноворкерный» описывал **дефект прода**
(синхронный вызов модели морозил цикл событий), а не свойство стенда. Дефект починили —
ограничение отпало.
