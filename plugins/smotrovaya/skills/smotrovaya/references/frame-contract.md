# Контракт снимка

Снимок — единица ленты. Всё, что о нём известно, записано в его имени и в манифесте
прогона; ничего не восстанавливается по памяти.

## Имя файла

```
output/<версия>/<сценарий>/<экран>__<состояние>__<аккаунт>__<шаг>__<устройство>.png
```

| Часть | Что значит | Правило |
|---|---|---|
| `<версия>` | `<хэш-кода>[-wip].<ММДД-ЧЧММ>[-<метка>]` | **пара (код, прогон)**, не один код |
| `<сценарий>` | идентификатор пути пользования | строчные латинские с дефисом |
| `<экран>` | смысловой экран продукта | **не момент сценария**: состояние идёт в `<состояние>` |
| `<состояние>` | что с данными на этом экране | `empty`, `loading`, `interpreted`, `after-edit` |
| `<аккаунт>` | чьими глазами снято | владелец · приглашённый · тренер · посетитель |
| `<шаг>` | порядковый номер в ленте | двузначный, сохраняет порядок прогона |
| `<устройство>` | `desktop` / `mobile` | **измеряется** у страницы, не объявляется |

**`-wip` означает незакоммиченные правки в дереве** — и только это. Метка прогона
(`<ММДД-ЧЧММ>`) отличает два прогона одного и того же кода; без неё второй прогон затирает
первый, и сравнение «до правки / после правки» становится невозможным.

История дефекта, ради которой правило записано: сначала любое грязное дерево давало просто
`<хэш>-wip`; первая починка привязала метку к грязности и **оставила ту же дыру на чистом
дереве** — поймано сразу после коммита, когда прогон снова лёг в безымянную папку.

## Манифест прогона

Рядом со снимками сценария — `manifest.json`: по шагу на запись.

```json
{
  "id": "two-children", "title": "Двое детей и история", "version": "8ddbf19.0824-2017",
  "steps": [
    { "step": 7, "screen": "analysis", "state": "interpreted", "account": "owner",
      "viewport": "desktop", "viewportWidth": 1280, "note": "разбор с пороговыми значениями",
      "file": "analysis__interpreted__owner__07__desktop.png", "ok": true, "error": "",
      "newFlow": false }
  ]
}
```

**`ok: false` с полным текстом ошибки — обязателен.** Обрезка ошибки до первой строки прячет
причину: движок браузера кладёт в первую строку заголовок, а улику («элемент перехватывает
клики», счётчики повторов) — ниже. Обрезка стоила одного живого прогона, потраченного на
добывание того, что уже было записано.

**Манифест пишется всегда** — и при сломанном прогоне тоже. Снимки и таймлайн есть
единственный способ понять причину; терять диагностику вместе с неуспехом нельзя.

## Идентификатор снимка и три строки замечания

Кнопка «ИД» в ленте кладёт в буфер **три строки**:

```
[Смотровая] 8ddbf19 · two-children · снимок 7/17 · analysis@owner · interpreted
frontend/e2e/deck/output/8ddbf19.0824-2017/two-children/analysis__interpreted__owner__07__desktop.png
frontend/e2e/deck/scenarios/two-children.deck.spec.ts → screen: 'analysis', state: 'interpreted'
```

1. **Адрес кадра** — человеку: что и чьими глазами.
2. **Путь к файлу** — агенту: открыть снимок.
3. **Сценарий и шаг** — агенту: найти место в сценарии и восстановить код прогона
   (`git show <версия>`).

Третья строка обязательна **потому, что каталог снимков живёт вне git** и однажды будет
вычищен. Без указателя на сценарий идентификатор старого прогона становится нечитаемым.

**Четвёртая строка — узел спеки** — добавляется, если в проекте закрыта точка
`module-contracts`: тогда замечание доходит до нарушенного обязательства, а не до места в коде.

## Аннотации — поле человека

Отдельный файл `annotations.json`, ключ `<сценарий>::<экран>`: «что здесь смотрим и зачем».
**Переживает перегоны** — в этом весь смысл: снимки пересоздаются каждым прогоном, а вопрос,
ради которого экран снимают, живёт дольше кода.
