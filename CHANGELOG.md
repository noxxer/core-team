# Changelog

Все значимые изменения фреймворка. Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версионирование — [SemVer](https://semver.org/lang/ru/).

## [Unreleased]

Правки по итогам боевого использования: 172 сессии healthstat-team + сессии wushu-library-team.
Главное — **гейт памяти роли снят и заменён механизмом, который не зависит от событий гарнесса.**

### Измерено (а не предположено)
- **Хук `TaskCompleted` не срабатывал ни разу.** По стенограммам двух проектов (48 файлов, 951 МБ; контроль пройден — вывод `SessionStart` найден в 48 из 48): **143 закрытия задач, 0 блокировок**. Причина не в багах хука: у задачи **нет владельца-роли** — вход `TaskCreate` во всех 218 замеренных вызовах содержит только `subject`/`description`/`activeForm`. Гард ключевался по признаку, которого фреймворк никогда не заполнял.
- **Дефект, ради которого гейт существовал, — настоящий.** Сверка «дата последнего прогона роли ↔ дата её памяти»: **у 10 ролей из 22, которые реально работали, память старше последней работы** (brand −25 дней, product −10, cfo −9, dev −4, architect/test −2). Действующий гейт ловил из этого ноль.
- **Единица работы роли — прогон субагента, а не задача:** 293 прогона против 0 срабатываний `TaskCompleted`. `facilitator` при этом не запускается как субагент ни разу — любой гард на событиях субагента его не покрыл бы.

### Removed
- **`hooks/verify-task.sh` и его проводка `TaskCompleted`.** Гард с доказанным нулевым покрытием — это декорация; по A.11 «add only what you cannot subtract» он снят, а не починен. Вместе с ним ушли режимы `observe/enforce`, журнал `.claude/verify-task.log` и конвенция `[role]` в теме задачи, которая существовала только чтобы дать гейту вход.
- **`.claude/hooks/hooks.json` — Claude Code его не читает.** Этот путь принадлежит плагинам (`~/.claude/plugins/*/hooks/hooks.json`); проектные хуки объявляются в `.claude/settings.json`. Файл выглядел конфигурацией и ею не был, а `CLAUDE.md` называл его «Конфигом» — потребитель, скопировавший только `.claude/hooks/`, получал ноль хуков. Класс дрейфа «построено ↔ подключено».
- **Устаревшая копия исходника хука в `knowledge/guide-multi-agent-teams.md`** — инструкция учила потребителя писать ровно тот вакуозный гард. Заменена разбором: почему у фреймворка один хук, и как проверить, что он вызывается.

### Added
- **Оркестратор приземляет память роли.** Каждая роль возвращает последним разделом отчёта блок «Для памяти роли» (дата, что сделано, решения, следующий шаг); facilitator дописывает его в `project/roles/<role>/context.md`, если записи за этот день там нет, а при отсутствии блока — фиксирует пропуск явно. Проверка снятого гейта переехала туда, где исполняется гарантированно: в цикл диспатча. Память стала побочным продуктом конвейера, а не долгом дисциплины.
- **Термометр памяти ролей в `SessionStart`.** Печатает роли, чья память отстаёт больше `MEMORY_STALE_DAYS` (по умолчанию 7) или пуста, разделяя два диагноза. Поставлен на единственное событие с подтверждённой частотой срабатывания. На реальных данных находит ровно те роли, что были найдены разбором стенограмм.
- **`hooks/session-start.test.sh` — доказательство мутацией** для термометра: 6 случаев (включая защиту от ложного срабатывания и от падения хука при отсутствии `project/`), **3 красных** на версии до правки.
- **CI `guards`** (`.github/workflows/guards.yml`) — первый механический потребитель красноты во фреймворке: прогоняет `hooks/*.test.sh` и `shellcheck`. Падает при **пустом наборе тестов** (перечисляющая проверка на пустом множестве проходит по построению).
- **Шаг проверки проводки хуков** в чеклисте установки и в Шаге 9 `/setup-project`: «файл лежит» ≠ «хук вызывается».

### Changed
- **Конституционный гейт стал пятишаговым: `Detect → Fix → Guard → Prove → Document`.** Фреймворк требовал, чтобы инвариант-тест **был**, и нигде не требовал показать, что он **краснеет в мире с дефектом**. Шаг **Prove** задаёт форму доказательства: назвать мутацию, подтвердить дифом, что она попала, мутировать в той форме, в какой дефект встречается в коде, приложить красный и зелёный прогоны. Выжившая мутация читается как «тест проходит другим путём», а не «код не нужен».
  - **Граница, чтобы правило не стало ритуалом:** доказательство обязательно там, где тест написан ПОСЛЕ кода (гард против класса дефектов, инвариант, проверка по следам бага). TDD-тест новой фичи освобождён — RED-фаза и есть его доказательство. В одну строку: **не видел свой тест красным — докажи мутацией.**
  - **Три структурные проверки, которых мутация не заменяет:** половина «найдено не ноль» у перечисляющих гардов; непустота сторон прежде равенства в сверках; названный потребитель красноты.
  - **Основание:** **69 уроков ремесла из 175 (39%)** в двух проектах касаются гардов; аудит собственных приборов нашёл **9 гардов**, не различавших мир с дефектом и без; в другом проекте ревьюер снял защиту двумя мутациями, которых автор не пробовал, — покраснело **0 тестов из ~44**.
  - **Термины заведены в словарь** `dpf/code-review.md`: гард, **ложно-зелёная проверка** (в уроках — «вакуозный гард»), мутационная проба, половина «найдено не ноль» — с колонкой «не является». Термин в документе без записи в словаре — дефект.
  - **Деградация для проектов без кода:** аналог мутации — показать, что проверка отвергает заведомо негодный образец (сфабрикованное число, недоступный источник, неполный артефакт).
  - Правило прошито в восьми точках: `core-protocols.md`, `CLAUDE.md` (структурный гейт №3), чеклист `test` (гард без доказательства → **P1**), `dev` (гард сдаётся вместе с мутацией), `tdd-master` (**три лица вакуозной проверки** вместо одного «The Liar»), `dpf/code-review.md` (**новый паттерн P-13**), `dpf/development.md` (**разграничение mutation score ⊥ mutation proof**, A.7) и **`hooks/session-start.sh`** — стартовый контракт каждой сессии, единственное место с подтверждённой частотой исполнения. Само распространение защищено гардом: `session-start.test.sh` краснеет, если правило выпадет из контракта.
- **`dpf/code-review.md`:** +P-13, +3 антипаттерна (Guard Without Proof, Vacuous Enumeration, Empty Comparison), +строка карты противоречий. Закрыт пробел, объявленный самим DPF в журнале сборки: «mutation testing упомянут в глоссарии, но нет паттерна».

- **Поле `enforced_by` в шаблоне решения + машинный проверщик.** У решения появился адрес проверки, делающей его нарушение красным.
  - **Замер:** 113 решений в двух проектах — слова «тест/гард/CI» встречаются в **111**, конкретный путь до проверки — в **8 (7%)**. При этом **75 записей реестра дрейфа из 108 (69%)** — класс «решение ↔ код», ещё 9 — «артефакт ↔ решение». **78% всей найденной в системе лжи — решения, разошедшиеся с реальностью.** Проблема не в осведомлённости, а в отсутствии адреса.
  - **Три легальные формы значения:** путь до проверки (`tests/test_x.py::test_y`), «гарда нет — держится на внимании роли `<role>`», «неприменимо — `<почему>`». Пустое и расплывчатое («покрыто тестами») адресом не является. Вариант «гарда нет» **обязан** оставаться разрешённым: запрет породил бы фиктивные гарды — шаг Prove наоборот.
  - **Связка с Prove:** названная проверка обязана быть доказана мутацией. Адрес, ведущий к недоказанному гарду, — это «гарда нет», а не закрепление.
  - **Оси разведены:** `kill_criteria` (смерть) ⊥ `review_due` (время) ⊥ `metric_for_revisit` (устаревание) ⊥ `enforced_by` (исполнение сейчас).
  - **`hooks/check-decisions.sh`** — проверщик с доказательством мутацией (`check-decisions.test.sh`, **14 случаев, 8 красных** на заглушке «всё годно»), вызывается из `/end-session` (Шаг 6a), подхватывается CI `guards`. Читает только шапку файла; принимает адрес по **белому списку** форм; файл `DEC-*` без шапки считает находкой, а не пропуском; при файлах без единого разобранного решения падает (половина «найдено не ноль»).
  - **Наследие:** решения старше даты внедрения перечисляются отдельно и проверку не роняют — заполняются **при первом касании** (цитирование, пересмотр, найденный дрейф).
  - Прошито: `templates/project/adr-template.md`, `/end-session` Шаг 6a, `agents/cto.md` (заполняется при ратификации), `agents/test.md` (сверка адреса на ревью), термин **«закрепление решения»** в словарь `dpf/tech-strategy.md`.

- **Контур возврата уроков во фреймворк (Harvest).** У фреймворка был контур обучения внутрь проекта и не было — наружу.
  - **Замер:** два проекта дописали в свои локальные `.claude/CLAUDE.md` **семь правил уровня фреймворка**, ни одно не вернулось в upstream. Одно из них — «правило без адреса в коде не реализовано» — **независимо переоткрыто вторым проектом два месяца спустя**: цена потери уплачена дважды. В другом найдена поправка к нашему же шагу Prove («нельзя мутировать вызов, которого нет»), которой у нас не было.
  - **Канал наверх уже существовал** (`CONTRIBUTING.md` + шаблон issue) — не хватало сборщика. Правка строит сборщик, а не второй канал.
  - **Критерий из промпта не отбирает.** «Нет ни одного слова предметной области» на 176 уроках даёт **132 кандидата** при семи настоящих (точность ~5%). Сильный сигнал другой: **проект уже дописал правило себе в файл фреймворка** — он проголосовал руками. Отсюда маркер `<!-- upstream-candidate: <корзина> — <почему> -->`.
  - **Корзин три, а не две:** ядро / `knowledge/stacks/<стек>/` / `project/dpf/`. Отдельно измерено: **23 урока из 176 (13%)** универсальны для стека, но не для ремесла — по бинарному критерию они уехали бы в ядро и засорили его. Предметное наверх не едет.
  - **`hooks/collect-upstream-candidates.sh`** — сборщик с доказательством мутацией (**14 случаев**, 10 красных на наивной заглушке, 2 — на варианте «считает документацию»). Корзина по белому списку, причина обязательна, документация формата (блоки кода и обратные кавычки) находкой не считается — иначе прибор показывает собственную настройку.
  - **`templates/project/framework-feedback.md`** — накопитель: открытые находки, отправленное наверх, «не поедет — почему», порог отправки (≥3 находки или 20 сессий).
  - Прошито: **`/end-session` Шаг 6b (Harvest)** с git-сверкой неотмеченных правок, структурный гейт №7 в `CLAUDE.md`, `/self-service`, `CONTRIBUTING.md` (issue пишется из накопителя), термин **«кандидат наверх»** в словарь `dpf/knowledge-keeping.md`.
- **Гард в CI на класс `«$var»`** — bash забирает первый байт многобайтового символа в имя переменной, `set -u` роняет скрипт. Класс пойман **дважды за одну сессию** в собственном коде; проверка красна на до-фикс файле и чиста на текущих.

- **Рефлексия вернулась к Founder, а сессия получила «зачем».** Две связанные правки по прямому наблюдению Founder: «перестал видеть работу рефлексии и Навигатора».
  - **Замер опроверг очевидное объяснение.** Navigator-анализ **не исчезал**: он есть в 68–75% недавних сессий (9 из 12 и 15 из 22 в августе) и занимает 8–17% файла `session.md`. Но **в итоговый отчёт Founder-у он попадает в 27% случаев (6 отчётов из 22)**: формат вывода `/end-session` состоял из пяти разделов, среди которых не было ни одного про смыслы. Работа делалась в файл, а читают — чат. Класс «построено ↔ подключено», третий раз за этот MR.
  - **Слот определяет результат — измерено на 210 сессиях.** В шаблоне `session.md` был **один** слот из четырёх инструментов. Iceberg (слот есть) — 36 и 26 сессий; Trap Scan — 19 и 17; System Operator — 7 и 12; Три «Почему» — **4 и 7**. Разница в 5–9 раз не про ценность инструмента, а про наличие места.
  - **Формат вывода `/end-session`** получил обязательный раздел «Смыслы и ловушки» — 4–6 строк в чат: структура (Iceberg) · почему сейчас (Три «Почему») · слепые зоны (System Operator) · ловушки сессии.
  - **Шаблон `session.md`** получил слоты под все четыре инструмента; старый раздел «Паттерны (Iceberg Model)» убран — один инструмент, один дом.
  - **`hooks/check-session-reflection.sh`** — проверщик непустых слотов последней сессии, с доказательством мутацией (**10 случаев**, 6 красных на заглушке). Подсказка шаблона в скобках и одинокая цитата заполнением не считаются; «не обнаружены» — считается. Сессия по старому шаблону распознаётся как унаследованная.
  - **Лестница смыслов в начале сессии.** `ledger.md` получил секцию **«Зачем»** (миссия → цель фазы → ближайший шаг, одна строка на уровень), хук `session-start.sh` печатает её при каждом старте, facilitator первой репликой связывает тему сессии с лестницей. Не сложилось связать — это находка, а не мелочь.
  - **Гард против хроники.** Замер: в боевом `ledger.md` поле фазы за 172 сессии превратилось в пересказ последней сессии, а `current_omtm` — в журнал с десятью архивными строками. Смысл вытесняется лентой событий, поэтому поле длиннее 200 символов помечается как хроника. Термин **«лестница смыслов»** — в словарь `dpf/facilitation.md`.

### Fixed

## [5.0.0] — 2026-06-29

DPF-слой: предметные учебники ремесла для каждой роли + intake-протокол фасилитатора + полный FPF-индекс. Реализация идеи DPF (Domain Principles Framework) из практикума А. Левенчука (28.06.2026): экосистема **FPPS → FPF → DPF → LPF**.

### Added
- **DPF-слой (Domain Principles Framework)** — недостающее звено между общим FPF и локальными артефактами проекта. Предметные SoTA-ходы/термины/ошибки/границы, упакованные в FPF-паттерны (E.8: ситуация→силы→ход→последствия→**антипаттерны**→связи→«когда НЕ»→источник→проверка).
- **Skill `dpf-builder`** — переиспользуемый метод постройки DPF: Collect (11 каналов сбора, вкл. плейбуки топ-5 компаний, стандарты/сертификации, постмортемы, конкурирующие школы, метрики) → FPF-process (упаковка в паттерны) → Loop-improve (E.21, draft→reliable). + `references/collection-protocol.md`.
- **11 role-DPF** (`.claude/knowledge/dpf/`) — сгенерированы через web-research + verify отдельным проверяющим (E.21). Flagship `facilitation.md` (13 паттернов): полный обход thecoreprotocols.org + Holacracy IDM + IAF + Kaner + Schwarz + Liberating Structures + Edmondson + Parker + литература провалов многоагентных систем (MAST).
- **Intake-протокол фасилитатора** (capture-first): хаотичный вход Founder → `project/inbox.md` → триаж по типам (task/tension/decision/question/idea/fact) → маршрутизация по протоколам. Шаблон `templates/project/inbox.md`. Инвариант: потерянный вход = процессная ошибка.
- **DPF в setup-project** (Шаг 4b): domain-DPF проекта + project-overlay на активные роли + чистка DPF неактивных ролей.
- Шаблон `templates/dpf-template.md`; каталог `knowledge/dpf/README.md` (онтология экосистемы).

### Changed
- **Facilitator пересобран (гибрид).** Аддитивная база: + чтение facilitation-DPF и `inbox.md` в ритуале, + функция Intake&Triage, + защита от ложного консенсуса [P-13]. Существующие протоколы (Decider/Resolution/Perfection Game/Clarity) сохранены и связаны ссылками `[P-NN]`.
- **Все роли читают свой DPF** в активационном ритуале (6 ядровых агентов + 5 opt-in шаблонов).
- **FPF-индекс: lite → полный**, пересобран под FPF-Spec @`40b232f` (i-m-senior-developer v1.4.1): +33 паттерна (слой архитектуры `C.32.*`, этика `D.1–D.4`, **`E.4.DPF/PFR/PFAD` авторинг экосистемы FPF**, онбординг `A.0`), −32 устаревших ID. Pin обновлён в `UPSTREAM-SYNC.md` + `fetch-fpf-spec.sh`.
- **`/self-service` implant** теперь строит role-DPF новой роли через `dpf-builder`.
- **Финальный гейт setup (Шаг 9)** расширен: DPF-связность + дедуп + противоречия в конструкции пользователя.

### Fixed
- **Противоречие immutability vs DPF-чистка.** `.claude/knowledge/dpf/**` явно выведен из-под правила «knowledge/** неприкосновенен» (CLAUDE.md + self-service) — это генерируемый слой (имплант добавляет, setup чистит).

## [4.5.1] — 2026-06-24

Упаковочный фикс: шаблоны проекта не доезжали до потребителя + прояснена модель установки.

### Fixed

После `git clone` + `cp -r .claude` они отсутствовали в проекте, и роли помечали это как tension (T-001), создавая артефакты «по структуре напрямую». Паттерны якорены: `/_migration/`, `/project/`.

## [4.5.0] — 2026-06-22

Дистилляция v5 в одно dev-ядро на subagent-архитектуре.

### Added (структурные гейты)
- **CHK-WIRE / CHK-ORPHAN** в роли `test` + правило «review проходит прод-путь вживую» — против wire/contract drift (самый дорогой класс багов: 5 проектов).
- **Detect → Fix → Guard → Document** — конституционный принцип в `core-protocols.md`.
- **Express-Parallel Protocol** — фоновые агенты в непересекающихся file-ownership зонах + пост-верификация `ls`/`git status`.
- **Гейт решений** в `/end-session`: `DEC-NNN ⟹ файл`, pending-DEC с owner+deadline, **same-session DEC-propagation**, publish-with-task.
- **Ledger git-verified** — лёгкая сверка «done»-заявок с `git log` всегда, полная reconciliation по триггеру `[STUB]`.
- **Explicit model selection** обязателен на каждый dispatch (против 3-5x перерасхода на унаследованном Opus).
- Шаблон `project/resources.md` — research-overlay.
- **FPF fetch-on-demand:** `skills/fpf-integration/scripts/fetch-fpf-spec.sh` — полная спека (~8.7MB) качается в глобальный кеш по требованию, не бандлится (подход из i-m-senior-developer). Lite-набор (glossary + tasks-lookup + sections-map + grep-patterns) = degraded-режим.

### Changed
- Ядро ролей сокращено до **6 dev-ролей** (facilitator, architect, dev, test, cto, keeper), активных по умолчанию.
- `keeper` объединяет glossary/domain + llms.txt + archivist (сжатие промптов).
- **FPF — рабочий инструмент фасилитатора** (не lite-заглушка): NQD/Evidence Graph/Bounded Context/DRR/Cynefin в Pre-DEC checkpoint + ADR-шаблоне; навигация по полной спеке через fetch-скрипт.

### Moved (opt-in, не активны по умолчанию)
- `product`, `guardian`, `analyst`, `designer`, `customer` → `templates/roles/optional/`. Подключаются через `/setup-project` / `/self-service`.

### Removed (мёртвый вес)
- Из активного набора по умолчанию убраны бизнес/контент-роли (см. Moved). Skills и knowledge сохранены — дистилляция сузила активную поверхность.
- Полный `FPF-Spec.md` (~8.7MB) не бандлится (качается по требованию) — но навигация по нему сохранена полностью.

### Принцип релиза
Сужен **активный набор по умолчанию**, формулировки и шаблоны сохранены. Ценность фреймворка — движок памяти и непрерывности (ledger/handoff, per-role context, hooks, planner-context), а не каталог ролей.
