# Core Protocols — Протоколы принятия решений

> Основано на McCarthy Core Protocols, Holacracy 5.0, Six Thinking Hats (de Bono).

---

## Протокол вопросов (3 стадии) — ОБЯЗАТЕЛЬНЫЙ

**Цель:** предотвратить потерю tensions и сократить обращения к основателю.

### Процесс

1. **TaskCreate** — ЛЮБАЯ tension, вопрос, проблема → сначала зафиксировать как задачу. Без фиксации — обсуждение запрещено
2. **Роли обсуждают** — Facilitator маршрутизирует tension к ролям через commands или Agent Teams. Роли анализируют, предлагают варианты
3. **Только потом к Founder** — если роли не могут разрешить tension самостоятельно → `AskUserQuestion` с вариантами и описанием последствий

**Нарушение:** задавать вопрос Founder без стадий 1-2 = процессная ошибка.

### AskUserQuestion — формат с последствиями (обязательно)

Каждая опция в `AskUserQuestion` **обязана** содержать:

1. **Краткое название** (1-3 слова)
2. **Что произойдёт при выборе** — последствие в терминах продукта / пользователя / системы
3. **Что НЕ произойдёт** — явное исключение, чтобы Founder понял scope

**Антипаттерны:**
- Open-ended «Что думаешь?» / «Как тебе?»
- Варианты без последствий (просто названия)
- Опции без явных trade-off-ов между ними

**Группировать 2-4 вопроса за один вызов** AskUserQuestion. Не перегружать Founder одиночными вопросами.

**Reason:** Founder должен видеть **информированный выбор**, а не угадывать что выйдет из каждой опции. Это compact-safe (вопросы переживают сжатие контекста) и сокращает повторные вопросы.

## Inventory-and-Proposal Protocol

**Цель:** предотвратить дорогие ошибки в крупных или необратимых операциях.

### Когда применять (триггеры)

Subagent **обязан** показать inventory-and-proposal до исполнения, если выполняется хотя бы одно:

- Работа с **внешней системой** (загрузка/выгрузка, API mass-write, миграция данных)
- **Batch ≥10 объектов** (массовое создание/обновление/удаление артефактов или записей)
- **Необратимая операция** (удаление, миграция схемы БД, публикация контента, изменение production)
- **Долгая локальная обработка** (≥10 минут на CPU/IO — транскрипции, конвертации, build)
- Работа с **более чем одной bounded context** одновременно

### Процесс

1. **Inventory** — что обнаружено: структура входа, найденные сущности, их количество и типы
2. **Proposal** — таблица «что → куда → обоснование» (или эквивалентный формат для домена)
3. **Спорные / неоднозначные пункты** — явный отдельный блок
4. **Открытые вопросы** для Founder через `AskUserQuestion` (с последствиями)
5. **Ожидание явного «ок»** от Founder — только после этого исполнение

### Что это НЕ значит

- НЕ требуется для S-операций (≤9 объектов, обратимые, локальные)
- НЕ требуется внутри уже одобренного pipeline (например, на каждой итерации loop-а)
- НЕ заменяет TaskCreate / AskUserQuestion — это **дополнение** на стадии "до делать"

## Express-Parallel Protocol (фоновые агенты без коллизий)

**Цель:** распараллелить работу нескольких subagent-ов без конфликтов записи.

**Ключевое правило:** фоновые агенты запускаются только в **непересекающихся зонах владения файлами на уровне файловой системы** (код vs артефакты vs спецификация). Зоны disjoint → нет гонок записи by design (FPF A.1.1 на уровне файлов).

**Волна** — два и более субагента, запущенных параллельно. Каждый идёт своей **дорожкой**: своя зона файлов, своя приёмка.

### Процесс
1. Facilitator/orchestrator декомпозирует задачу на дорожки и назначает каждой **непересекающийся набор путей** (например: дорожка A пишет `src/`, дорожка B — `project/artifacts/`, дорожка C — `docs/`). Каждая получает бриф по форме `.claude/templates/dispatch-brief.md`, в котором **приёмка названа до запуска**
2. Проверка disjoint: пересечение путей пусто. Есть пересечение → не параллелить, резать иначе. **Единственный на контур ресурс** (стенд, общая база, платный внешний вызов) не делится зонами — он получает владельца на время работы, названного в брифе. Замер: «в единоличное владение» отдан файл, в который писали все дорожки; и TDD-дорожка на общем стенде дала 15 перезапусков за 20 минут, отравив живой прогон
3. Запуск ≤7 агентов (см. `cost-model-discipline.md`)
4. После волны — **приёмка дорожек по файлам, а не по отчётам**: `.claude/hooks/check-lane-acceptance.sh --since <старт волны> <приёмка-1> ...`. Отчёт агента бывает бодрым при потерянной работе; `--since` дополнительно отсекает наследие прошлого прогона. `ls` + `git status` остаются как сверка «записано туда, куда заявлено»
5. **Перед респауном упавшей дорожки — сначала приёмка.** Дважды упавшие агенты оставляли готовые файлы, и респаун был бы дублем. Дорожка не доехала → разбирается как дефект брифа: какое поле было пустым

**Reason:** на практике даёт 0 коллизий и кратно меньше wall-clock против последовательной работы. Без disjoint-зон параллельные агенты затирают записи друг друга. Без названной приёмки терялась работа целиком: **три дорожки из шести** писали результат последним действием, и падение уносило всё.

## Detect → Fix → Guard → Prove → Document (конституционный)

**Цель:** не допустить повторения класса багов.

> «Правило без гарда — это просто мнение. **Гард без доказательства — тоже мнение, просто зелёное**»,
> и он опаснее отсутствующего: он снимает вопрос и создаёт ложную защищённость.

Каждый обнаруженный **класс** ошибки (не единичный баг) проходит 5 шагов:

1. **Detect** — зафиксировать класс: что именно сломалось и почему (корневая причина, не симптом)
2. **Fix** — починить конкретный случай
3. **Guard** — добавить **machine-verifiable инвариант-тест**, который падает на этом классе
4. **Prove** — показать, что гард **краснеет в мире с дефектом**
5. **Document** — записать класс + гард + мутацию в ADR / context.md роли, чтобы знание пережило сессию

### Шаг Prove — форма доказательства

- **Назови мутацию.** «Проверено мутацией» — незаконченное утверждение: значение имеет, каким
  именно изменением дефект возвращён.
- **Подтверди дифом, что мутация попала** туда, куда заявлено. Замена «первого вхождения» умеет
  попасть в соседний файл — гард при этом честно молчит, потому что предмет проверки не менялся.
- **Мутируй в той форме, в какой дефект встречается в коде**, а не в выдуманной. Проба на
  несуществующей форме доказывает, что гард работает, но не что он ловит то, от чего защищает.
- **Приложи оба вывода** — красный до, зелёный после. Устного «проверил» не бывает.
- **Выжившая мутация ≠ «код не нужен».** Это значит «тест проходит другим путём»: назови путь,
  отрежь его в сценарии, повтори мутацию. Признак успеха — красное сообщение совпадает с
  утверждением теста.

**Когда доказательство обязательно:** всегда, когда тест написан **после** кода — то есть когда
дефекта в момент написания уже нет и краснота не наблюдалась. TDD-тест новой фичи освобождён:
RED-фаза и есть его доказательство.

> Правило в одну строку: **не видел свой тест красным — докажи мутацией.**

**Проекты без кода (research, стратегия, контент).** Гейт конституционный — он для всех типов,
но мутировать там нечего. Аналог мутации: **показать, что проверка отвергает заведомо негодный
образец** — подсунуть сфабрикованное число, недоступный источник, неполный артефакт и убедиться,
что проверка это ловит. Проверка, принимающая заведомо негодный вход, ничего не проверяет,
независимо от того, код это или текст.

**Когда НЕ применять:** контур, который нельзя безопасно мутировать (живая оплата, прод-БД,
внешний сервис) — там фиксируется краснота ДО починки, а не создаётся дефект.

### Три структурные проверки, которых мутация не заменяет

- **Половина «найдено не ноль».** У любого *перечисляющего* гарда (модули, маршруты, файлы, строки
  конфига) два способа быть зелёным: нарушений нет — или перечисление пусто. Второй проверяется
  отдельной половиной и живёт в том же файле. Пустое перечисление устойчиво: оно переживает
  рефакторы и переезды, ничем себя не выдавая.
- **Непустота прежде равенства.** В любой сверке сначала утверждается непустота каждой стороны, и
  только потом равенство. Отказ инструмента не должен совпадать с самым благополучным ответом:
  сверка md5 напечатала «совпадает» по всем файлам ровно потому, что команды не нашлись и
  сравнивались пустые строки.
- **Кто потребляет красноту.** Красный тест, который никто не запускает и который ничего не
  останавливает, гардом не является. У гарда всегда назван потребитель: CI, хук, гейт ревью.

**Триггер:** баг, который «уже встречался» или может встретиться снова. Единичная опечатка — не
требует гарда.

**Reason:** полевые данные двух проектов — **69 уроков ремесла из 175 (39%)** касаются гардов и
проверок; в одной сессии аудит собственных приборов нашёл **9 гардов**, не различавших мир с
дефектом и без; в другой ревьюер снял защиту двумя мутациями, которых автор не пробовал, — и
покраснело **0 тестов из ~44**. Тест пишется сразу после кода, тем же автором, в тех же терминах —
и наследует его слепые зоны. Разделяет «зелёный» и «поймает регресс» ровно одна процедура.

## Clarity Protocol (перед решением)

**Цель:** убедиться, что все понимают одно и то же, прежде чем решать.

### Процесс
1. Формулировка: что именно решаем? (одно предложение)
2. Проверка 8 точек:
   - [ ] Путь пользователя описан конкретно
   - [ ] Допущения названы явно
   - [ ] Ресурсы оценены
   - [ ] Сроки определены
   - [ ] Границы scope зафиксированы
   - [ ] Legal/compliance учтено
   - [ ] Нет "серых зон" — неясных ответственностей
   - [ ] Критерии успеха измеримы
3. Если хоть одна точка не закрыта → уточнить ДО перехода к Decider

### Red Flags (немедленная остановка)
- "разберёмся потом"
- скрытые допущения ("это же понятно")
- отсутствие дедлайнов
- абстрактный scope ("сделать хорошо")
- "это же очевидно" (ложный консенсус)

## Decider Protocol (голосование)

**Цель:** быстрое и явное принятие решения.

### Процесс
1. **Clarity пройдена** (обязательно)
2. **Предложение** — формулируется одним предложением
3. **Голос основателя:**
   - **Да** — принимаю
   - **Нет** — не принимаю + обязательная альтернатива
   - **Поддержка-с-условием** — принимаю если [условие]
4. **Резолюция** — если "Нет":
   - Возражающий предлагает альтернативу
   - Clarity Protocol для альтернативы
   - Повторное голосование
5. **Запись:** `project/decisions/DEC-NNN_title.md`

### Формат решения (ADR)
```markdown
# DEC-NNN: Название решения

**Дата:** YYYY-MM-DD
**Статус:** Proposed | Accepted | Deprecated
**Контекст:** [Почему возник вопрос]

## Варианты

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| A | ... | ... |
| B | ... | ... |

## Решение
[Что выбрали и почему]

## Последствия
[Что изменится, на что повлияет]
```

## Perfection Game (обратная связь)

**Цель:** конструктивная критика без негатива.

### Процесс
1. Оценка от 1 до 10 (текущее состояние)
2. "Что добавить, чтобы стало 10?" (конкретные предложения)

### Правила
- Нельзя ставить оценку без предложений по улучшению
- Предложения должны быть конкретными и выполнимыми
- Автор не обязан принимать все предложения

## Check-In (начало сессии)

**Цель:** синхронизация состояния перед работой.

### Процесс (1 минута)
1. Текущее состояние (одно предложение)
2. Фокус сессии (что хотим достичь)
3. Ограничения (время, ресурсы, блокеры)

## Pass (право пропуска)

**Цель:** не блокировать процесс, если нечего добавить.

### Правила
- Любой участник может сказать "Pass" в любой момент
- Pass не требует обоснования
- Pass не означает несогласие — только отсутствие input

## Six Thinking Hats (режимы мышления)

**Цель:** структурированный brainstorm без хаоса.

| Шляпа | Фокус | Роль в команде |
|-------|-------|----------------|
| Белая | Факты, данные | Analyst |
| Красная | Интуиция, чувства | Customer |
| Чёрная | Критика, риски | Guardian |
| Жёлтая | Оптимизм, возможности | Product / Analyst |
| Зелёная | Креатив, альтернативы | Designer / Architect |
| Синяя | Процесс, управление | Facilitator |

### Применение
1. Facilitator объявляет шляпу
2. Все думают в режиме этой шляпы (5 минут)
3. Следующая шляпа
4. Синтез результатов

## Tension Processing (маршрутизация)

**Цель:** каждое "напряжение" находит адресата.

### Процесс
1. Кто-то ощущает tension (проблему, идею, вопрос)
2. Facilitator определяет домен → маршрутизирует к роли
3. Роль анализирует и возвращает рекомендацию
4. Если cross-domain → обе роли высказываются
5. Facilitator ведёт к решению через Decider

### Типы tensions
- **Операционная** — что-то не работает → к владельцу домена
- **Стратегическая** — куда двигаться → Product + Analyst
- **Рисковая** — что может пойти не так → Guardian
- **Ресурсная** — чего не хватает → CTO (технический ресурс) / Product (объём работ)

> Адресаты здесь — роли фреймворка. Проект вправе имплантировать свои (`/self-service`);
> тогда маршрут ведёт к ним, и таблица дополняется в проектной копии. Имя роли, которой
> в проекте нет, маршрутом не является: tension уходит в никуда и возвращается неразобранным.
