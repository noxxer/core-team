# Cost-aware Model Discipline

Дисциплина выбора исполнителя и параллелизма subagent-ов.

> **Выбор стал двумерным.** Раньше решение сводилось к одному вопросу — какая модель.
> Сегодня их два: **модель** задаёт класс способностей, **усилие** (`effort`) задаёт глубину
> рассуждения внутри класса. Sonnet на `xhigh` и Sonnet на `low` — разные исполнители по цене
> и по результату. Документ, знающий только первое измерение, систематически выбирает дороже
> и хуже: поднимает модель там, где хватило бы усилия.

## Принцип

> Default — Sonnet на дефолтном усилии. Модель поднимают за **классом способностей**,
> усилие — за **глубиной**. Haiku — для quick-pass.

При конфликте оптимизации и надёжности **побеждает надёжность**: security/data-migration/strategy всегда получают более умную модель + отдельный review.

## Измерение 1: модель

Псевдоним всегда предпочтительнее точного имени: он разрешается в актуальное поколение и не
протухает. Явные ID (`claude-opus-5`) — только когда нужно прибить версию намеренно.

| Псевдоним | Во что разрешается / для чего | Когда использовать |
|-----------|------------------------------|--------------------|
| **`sonnet`** | последний Sonnet — ежедневная работа | Default: dev, test, facilitator, keeper, designer, customer |
| **`opus`** | последний Opus — сложное рассуждение | architect, CTO, NQD на критическом решении, security audit высоких ставок |
| **`haiku`** | быстрый и дешёвый | Quick-pass, batch-обработка, lookup, заполнение шаблона по форме |
| **`fable`** | Fable 5 — самые трудные и **длинные** задачи | Кандидат для architect/CTO на многочасовой миграции или сквозном аудите |
| **`best`** | Fable, где он доступен, иначе последний Opus | Когда важен потолок, а не предсказуемость счёта |
| **`opusplan`** | opus в режиме планирования, sonnet на исполнении | Ровно наш конвейер architect → dev в одном агенте, когда не хочется двух ролей |
| **`opus[1m]` / `sonnet[1m]`** | миллионный контекст | Длинные сессии, сквозной разбор большого репозитория |

**Не использовать:** Opus на реализации по готовому ARCH, на рутинном ревью, на заполнении
шаблонов. Haiku — на архитектурных решениях, security-ревью и любой задаче, где цена ошибки
выше стоимости прогона.

## Измерение 2: усилие (effort)

`low` · `medium` · `high` (по умолчанию) · `xhigh` · `max`. Управляет тем, сколько модель
рассуждает на каждом шаге. Ставится в frontmatter роли (`effort:`), на сессию (`--effort`,
`effortLevel`) или переменной окружения. Уровень выше поддерживаемого моделью тихо опускается
до ближайшего поддерживаемого.

| Уровень | Когда |
|---------|-------|
| **`low`** | Механическая правка по готовому образцу, batch, форматирование |
| **`medium`** | Структурированная задача с чеклистом, где шагов много, а развилок мало |
| **`high`** | Дефолт. Обычная работа роли |
| **`xhigh`** | NQD ≥3 альтернатив, FPF-аудит, DRR, разбор противоречия между ролями. Стоит у architect и CTO |
| **`max`** | Разовая самая трудная развилка сессии. На роль не ставится — включается на сессию |

**Правило выбора между измерениями.** Задача структурирована, но глубокая (чеклист есть,
развилок много) → **поднимай усилие**. Задача неструктурирована или кросс-доменна (нечего
чеклистить) → **поднимай модель**. Поднимать оба сразу — законно только там, где цена ошибки
выше цены прогона.

## Default-модели по ролям (через subagent frontmatter)

|------|--------|--------|-------------|----------------|
| Facilitator | sonnet | — | Оркестрация, диспатч, фиксация решений — не творческая, но требует понимания контекста | На NQD-сессиях с большими альтернативами |
| Architect | **opus** | **xhigh** | Design-decisions с долгосрочными последствиями, FPF A.7/A.10/A.1.1 проверки | — (уже opus) |

## Параллелизм: ≤7 subagent-ов в фазе

Опираемся на LIFT-COT capacity-bounds (когнитивный лимит координации):

| Фаза | Макс. параллельных subagent-ов | Источник лимита |
|------|-------------------------------|-----------------|
| Planning (3-стадийный вопрос, NQD) | **6** | Когнитивный лимит на удержание альтернатив |
| Validation (ревью, тестирование) | **7** | Magic number 7±2 для перекрёстной проверки |
| Integration (имплементация) | **4** | Лимит на согласование интерфейсов между потоками |

Если задача требует больше — режь на последовательные фазы. Не запускай 12 архитекторов параллельно "на всякий случай".

## Pilot-then-batch (при ≥3 параллельных одного типа)

Когда в фазе планируется **≥3 параллельных subagent-а одного типа** (например, 4 architect для разных модулей или 5 evidence-check на разных артефактах) — обязательна **пилот-фаза**:

1. **Phase N.1 — Pilot:** запустить **1 subagent-а** с полным контекстом
2. **Калибровка** — facilitator/orchestrator анализирует output пилота, корректирует промпт остальных
3. **Phase N.2 — Batch:** запустить **N-1** оставшихся параллельно после калибровки

**Reason:** параллельные runs одного типа имеют общий риск (плохой промпт, недосказанная конвенция). Пилот — дешёвый detector. Без пилота 4-5 неудачных runs стоят дороже чем 1 пилот + 4-5 успешных. Проверенное правило на практике.

**Когда пилот НЕ нужен:**
- 2 параллельных subagent-а одного типа (overhead не оправдан)
- 3+ subagent-ов **разных типов** в одной фазе (общего промпт-риска нет)

Автодетекция и автоматическое разделение фазы — в `skills/planner/SKILL.md` (execution mode).

## Когда повышать модель (escalate)

Признаки, что нужен Opus вместо Sonnet:
1. **Высокая цена ошибки** — данные миграции, security, financial logic, архитектура с долгим жизненным циклом
2. **Неструктурированная задача** — нет чёткого ARCH/чеклиста, нужно проектировать решение
3. **Множественные альтернативы с trade-offs** — NQD требует ≥3 альтернатив с обоснованием
4. **Cross-domain reasoning** — нужно связать стэк/бизнес/legal/UX в одном решении
5. **Семантическая сложность** — bounded contexts с разными invariants, FPF A.1.1

## Когда понижать модель (downgrade)

Признаки, что Haiku справится с тем, что обычно делает Sonnet:
1. **Жёстко структурированная задача** — заполнение готового шаблона, форматирование
2. **Lookup в knowledge** — найти секцию, скопировать нужный фрагмент
3. **Batch-обработка** — одинаковая операция над N файлами
4. **Форматные правки** — переименование, перенос строк, индентация

## Орчестрация: правило стоимости

Перед запуском пайплайна с дорогими моделями (Opus в нескольких subagent-ах) — оценить:
- Tokens estimate (по объёму input)
- Wall-clock estimate (по числу фаз)
- Relative $-cost vs naive single-agent

Если cost > 5x от naive solution без явной выгоды — пересмотри плана. Может, достаточно одного Sonnet-subagent с расширенным контекстом.

## Прочие рычаги frontmatter роли

Модель и усилие — не единственное, что объявляется у роли. Всё это — механика вместо обещания
в промпте:

| Поле | Что даёт | Замер |
|------|----------|-------|
| `skills: [имя]` | навык **вливается** в контекст роли при старте | проверено: роль без единого инструмента процитировала дословные термины навыка |
| `effort:` | глубина рассуждения независимо от модели | принято без ошибок на 2.1.246 |
| `maxTurns:` | потолок числа ходов роли | защита от роли, ушедшей в цикл |
| `permissionMode:` | режим разрешений роли | read-only роль не получит прав на запись |
| `isolation: worktree` | роль работает в своём git-worktree | кодовые дорожки волны не сталкиваются на уровне ФС |
| `disallowedTools:` | вычесть инструмент из унаследованных | точнее, чем перечислять `tools` целиком |
| `memory: project` | своя персистентная память роли | родной аналог `roles/<role>/context.md` — решение уровня DEC, пока не внедрено |

Предзагружать навык стоит только там, где он нужен **всегда**: содержимое вливается целиком и
становится постоянным налогом на каждый прогон роли.

## Explicit model selection (обязательно)

Модель **и усилие** каждого dispatch subagent-а указываются **явно** — через frontmatter роли или параметр вызова. Запрещено молча наследовать модель родителя: унаследованный Opus в реализации/ревью даёт 3-5x перерасход без выгоды (повторяющийся перерасход). Перед `Agent(...)` сверься с таблицей default-моделей выше; отклонение от default — обоснуй одной строкой.

## Anti-patterns

- **Молчаливое наследование Opus** — subagent без явной модели наследует родителя → кратный перерасход
- **Opus "на всякий случай"** — каждый Opus-выбор должен быть обоснован
- **Все subagent-ы на Opus** — кратно дорого, редко оправдано
- **Один Opus-architect делает 12 фич сразу** — режь на последовательные фазы
- **Haiku на security review** — никогда; security всегда минимум sonnet, в идеале opus
- **Поднять модель там, где хватило бы усилия** — структурированную задачу с чеклистом дешевле углубить, чем переносить на класс выше
- **Ставить `effort: high` явно** — это и есть дефолт; запись без изменения смысла создаёт видимость решения
- **Предзагружать навык «на всякий случай»** — полное содержимое вливается в контекст при каждом прогоне роли
- **Явный ID модели вместо псевдонима** — привязка к поколению протухает молча, а псевдоним обновляется сам
- **Параллельный запуск без оценки cost** — кратные счета без выгоды
