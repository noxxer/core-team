# End Session — Закрытие сессии

Аргумент `$ARGUMENTS` — тема сессии (если пусто, определи по контексту).

## Шаг 1: Сбор контекста
1. `project/ledger.md` → последний handoff из `project/sessions/` → `TaskList` → определи тему

## Шаг 2: Обобщение выводов (Navigator)

### 2a. Iceberg Model — для каждого значимого результата пройди 4 уровня:
Событие (что произошло) → Паттерн (повторяется?) → Структура (что порождает) → Ментальная модель (убеждение за этим)
В session.md выноси **паттерны и структуры** — они полезны для следующих сессий.

### 2b. Three "Why?" — для каждого DEC-NNN:
Почему это решение? Почему важно для проекта? Почему сейчас? Нет чёткого ответа → OQ-NNN.

### 2c. System Operator — для ключевых решений:
Матрица 3x3: (Подсистема/Система/Надсистема) x (Было/Стало/Будет). Пустые ячейки = слепые зоны.

### 2d. Metacognition Checklist
- Выводы на правильном уровне? Альтернативы (>=3) для сложных решений?
- Проверка вверх (видение) и вниз (реализуемость)? Нет tunneling/premature closure/goal displacement?

### 2e. Итоговая фиксация

> **Анализ, оставшийся в файле, для Founder не существует.** Замер: Navigator-анализ есть в 68-75%
> недавних сессий, а в итоговый отчёт попадает в **27%** (6 отчётов из 22). Работа делается и до
> потребителя не доходит — класс дрейфа «построено ↔ подключено».
> Выводы каждого инструмента идут **и** в `session.md` (слоты раздела «Смыслы»), **и** в отчёт в чат.

Решения (DEC-NNN + "почему"), обновлённые артефакты, ключевые выводы (паттерны/структуры), слепые зоны, новые OQ-NNN.

### 2f. Конвертация находок в задачи — ОБЯЗАТЕЛЬНО
**Каждая** слепая зона, неотвеченный "почему", паттерн без решения → `TaskCreate` (указать источник, контекст, роли). Если после 2e остались находки без задач — протокол НЕ ЗАВЕРШЁН.

## Шаг 3: Ревизия задач
Пройди `TaskList`: завершённые → `TaskUpdate` completed | давно неактуальные → предложи удалить | можно объединить → предложи | блокированные → уточни блокер. Изменения через `AskUserQuestion`.

## Шаг 4: Trap Scan + опыт

### 4a. Ловушки сессии:
| Ловушка | Признак |
|---------|---------|
| Einstellung | Первый вариант без альтернатив |
| Tunneling | Долго без прогресса |
| Bike-shedding | Час на мелочь, минута на ключевое |
| Goal displacement | Процесс стал целью |
| Premature closure | Закрыли слишком быстро |
| Dead-level abstracting | Застряли на одном уровне |

Если были — зафиксируй: что, как заметили, как избежать.

### 4b. Паттерны работы, поведение ролей, проблемы процесса, новые конвенции → обнови auto-memory.

## Шаг 5: Глоссарий/домен (опционально)
Новые термины → `project/glossary.md`. Новые факты → `project/domain.md`. Устаревшие тезисы → обновить.

## Шаг 5a: Code-vs-Ledger Reconciliation (git-verified)

> **Лёгкая сверка — ВСЕГДА.** Перед записью любого статуса «done» в ledger сверь его с git: `git log --since="<session-start>" --name-only` и (если есть remote) `git branch -r --merged`. Ledger пишется **по факту кода/коммитов, а не по памяти** — иначе «done»-заявки расходятся с реальностью и переживают сессии.
>
> **Полная reconciliation (architect discovery) — по триггеру `[STUB]`:** в сессии обнаружен маркер `[STUB]` / `# STUB:` / `# TODO:` / «вернёмся позже» в коде, в `roles/<role>/context.md`, или в session.md / handoff. Нет триггера — ограничься лёгкой сверкой выше.

Запуск `Agent(subagent_type=architect)` в discovery-режиме:

1. Пройди по последним коммитам сессии (`git log --since="<session-start>" --name-only`)
2. Grep по `STUB|TODO|FIXME|placeholder` в изменённых файлах
3. Сравни с `project/ledger.md` — есть ли расхождение между «что записано» и «что в коде»?
4. Обнови `ledger.md` **по факту кода**, не по плану
5. Для каждого `[STUB]` маркера → создать `TaskCreate` с приоритетом для следующей сессии (что именно недостроено + где)

**Reason:** после stub-фаз ledger расходится с реальностью (G.2 staleness post-stub). Без явной reconciliation в следующих сессиях architect/dev исходят из устаревшей картины и плодят расхождения.

## Шаг 5b: Обновление контекстов ролей — ОБЯЗАТЕЛЬНО

> `context.md` роли — **состояние, а не журнал**. Хроника сессии пишется в
> `project/sessions/` (Шаг 7); дублировать её в память роли значит лишить память дна.

Для каждой роли, участвовавшей в сессии:
1. Прочитай `project/roles/<role>/context.md` и критерий приёма в шапке шаблона: здесь лежит только то, что **исчезнет, если не записать** — у состояния проекта, событий, решений, терминов и фактов о мире есть свои файлы
2. **Перепиши** разделы состояния: текущий фокус, рабочие знания, процессные заметки, **отвергнутые пути** (что пробовали и почему не сработало), **повторяющиеся ошибки роли**
3. Открытые вопросы — добавь новые и **убери закрывшиеся** (след остаётся в сессиях и решениях)
4. Обнови «Последние решения» (DEC-NNN) и «Уроки ремесла» — то, что куплено дорого
5. Обнови `last_updated` в YAML-заголовке
6. Прогони `bash .claude/hooks/check-role-memory.sh`

> **Это гейт, а не напоминание.** Хук `memory-gate.sh` не даст записать сессию (Шаг 7),
> пока проверщик красный, и не даст **дописать** датированный раздел в память роли:
> приземление идёт перезаписью разделов. Хроника дня живёт в `project/sessions/`.
> Файл выше предела чтения инструментом не открывается — разбирай его через `Bash`
> (`sed -n`, `awk`), а не `Read`.

Не трогай контексты ролей, которые НЕ участвовали в сессии.

**Красный вывод — не закрывай сессию по-тихому.** Три диагноза, три разных лечения:

| Что сказал проверщик | Что делать |
|---|---|
| **ПАМЯТЬ НЕ ЧИТАЕТСЯ** | Роль уже работает вслепую. Разбери файл сейчас: состояние — в `context.md`, хронику — в `project/sessions/`. Отложить нельзя: следующая сессия начнётся без памяти. |
| **ВЕДЁТСЯ ЖУРНАЛОМ** | Датированные блоки съезжают в `sessions/`, в память возвращается срез. Не «сожми», а **сверни в состояние**. |
| **ЗА БЮДЖЕТОМ** | Свернуть; либо поднять `max_lines` в шапке — осознанно и с причиной в этой же строке. |

> Замер (2026-08-26): у трёх самых нагруженных ролей боевого проекта память доросла до
> **571.5 / 334.5 / 303.5 КБ** при пределе чтения **256 КБ**. Активационный ритуал предписывал им
> читать свою память первым делом — у трёх из одиннадцати этот шаг был физически невыполним и
> проваливался молча. Термометр возраста при этом показывал «в норме»: он мерил свежесть.

## Шаг 6: Ревью промптов
Проверь `.claude/CLAUDE.md` и `.claude/commands/` на актуальность. SAFE-изменения — сразу, остальные — через `AskUserQuestion`.

## Шаг 6a: Гейт решений (pending-DEC) — ОБЯЗАТЕЛЬНО

> Проблема: решения «зависают» в статусе pending или живут только сжатой строкой в ledger без файла — обоснование теряется, заблокированная работа копится.

1. **DEC-NNN ⟹ файл.** Любой `DEC-NNN`, упомянутый в `ledger.md`, **обязан** иметь `project/decisions/DEC-NNN.md`. Нет файла → создать сейчас (по `adr-template.md`) или убрать упоминание. Сжатая строка ledger ≠ решение.
2. **Pending-решения.** Каждое решение в статусе `Proposed`/pending в этой сессии → либо ратифицировать в файл, либо явный **deferral с owner + deadline** (`TaskCreate`). Без owner+deadline pending-решение оставлять запрещено.
3. **Same-session DEC-propagation.** Если ратифицированный DEC меняет рабочий процесс (правила ролей, инварианты, конвенции) — в **этой же сессии** обнови: (1) `output-styles/` или `CLAUDE.md`, (2) TOP-строку `ledger.md`, (3) напоминание в `hooks/session-start.sh`, (4) чеклист затронутой роли. Иначе DEC «протухает» за 2-3 сессии.
4. **DEC ⟹ адрес проверки.** Прогони `bash .claude/hooks/check-decisions.sh`. Решение без `enforced_by` — намерение, а не правило: 69% записей дрейфа в замере — класс «решение ↔ код». Красный вывод → заполнить поле (адрес проверки / «гарда нет — держится на внимании роли <role>» / «неприменимо»). Унаследованные решения проверку не роняют — их заполняют при первом касании.
5. **DEC ⟹ не протух.** Прогони `bash .claude/hooks/check-decision-decay.sh`. Три находки, три лечения: *проверка просрочена* → продли `review_due` с причиной либо вытесни решение новым («действует по инерции» третьим вариантом не является); *нет даты проверки* → назначь её, иначе решение действует вечно; *порог без прибора* → назови `metric_for_revisit` или признай, что порога нет. Замер: из 177 решений в четырёх проектах 32 просрочили проверку, 85 не имели её вовсе, 45 назвали порог отмены без метрики. Унаследованные решения прогон не роняют.

6. **publish-with-task.** Если сессия обновила публичный артефакт с будущими обязательствами (обещания, награды, дедлайны вовне) → авто-`TaskCreate` с owner+deadline. Обещание без owner = забытый долг.

## Шаг 6c: Потолок реестра — ОБЯЗАТЕЛЬНО, если реестр ведётся

1. `bash .claude/hooks/check-registry-ceiling.sh` — открытых записей не больше объявленной ёмкости.
2. Посчитай **найдено ÷ закрыто за эту сессию**. Отношение больше единицы **две сессии подряд**
   означает, что команда научилась находить и разучилась закрывать: вынеси это Founder-у.
3. Потолок пробит → не дописывай молча. Либо новая находка **вытесняет** запись ниже приоритетом
   (и вытесненная закрывается решением «не чиним», а не исчезает), либо цель фазы меняется на
   «закрыть реестр до потолка» и это пишется в `ledger.md`.

> Замер: в боевом проекте реестр дошёл до **76 открытых против 32 закрытых** и рос на 12 за
> сессию. В такой реестр перестают смотреть — смотреть больше не на что, там всё.

## Шаг 6d: Требования — ОБЯЗАТЕЛЬНО, если файл ведётся

1. `bash .claude/hooks/check-requirements.sh` — у каждого требования есть источник обязательства, а у заявленного покрытия — адрес проверки.
2. Очередь не взятых выше ёмкости → назови исполнителя (того, кто **сдаёт** работу, а не следит) либо поднимай `unassigned_ceiling:` с причиной.
3. **Разведи смешанное.** Находка сессии попадает по признаку: уже случилось → дефект (задача); закрывается постройкой → требование; только снизить или принять → риск; утверждение о мире → допущение в решении; выбор вариантов → `DEC`; решение разошлось с кодом → дрейф. Порядок вопросов именно такой: иначе дефект уезжает в риски с вероятностью, которой у него нет.

> Замер: в боевом реестре рисков 16 записей из 18 были обязательствами. Раскладка 20 записей по признаку дала 10 требований, 5 рисков, 2 дефекта, 1 допущение, 1 решение, 1 дрейф — спорных ноль.

## Шаг 6b: Harvest — что из найденного универсально

> Контур обучения **наружу**. Замер: два проекта дописали в свои `.claude/CLAUDE.md` семь правил
> уровня фреймворка, ни одно не вернулось в upstream; одно было независимо переоткрыто вторым
> проектом два месяца спустя. Канал наверх открыт (`CONTRIBUTING.md` + шаблон issue) — не хватало сборщика.

1. Прогони `bash .claude/hooks/collect-upstream-candidates.sh`. Он находит места, где проект
   дописал в файлы фреймворка правило, помеченное `<!-- upstream-candidate: <корзина> — <почему> -->`.
2. Сверь с git: `git diff --name-only <начало-сессии> -- .claude/`. Файл фреймворка, изменённый
   **без** маркера, назови явно — поставь маркер сейчас или объясни, почему правка сугубо локальная.
   Маркер ставит человек; git показывает, где его забыли поставить.
3. Новые находки перенеси в `project/framework-feedback.md` (шаблон в `.claude/templates/project/`),
   указав корзину: **ядро** / **stacks/`<стек>`** / **project/dpf/** (последнее наверх не едет).
4. Достигнут порог (по умолчанию ≥3 открытые находки или 20 сессий) → предложи Founder оформить
   issue по `.github/ISSUE_TEMPLATE/feature_request.md`: мини-ADR из накопителя, NQD ≥3, последствия.

Ничего не найдено — раздел не пишется. Пустой шаг каждую сессию превращается в ритуал.

## Шаг 7: Запись артефактов

**Условие выхода — первым делом.** Перенеси в `session.md` условие, объявленное фасилитатором в
начале сессии, и вынеси вердикт. Не достигнуто — так и запиши: незакрытое условие переезжает в
handoff как первый пункт. Подгонять формулировку под то, что вышло, запрещено — это способ
никогда не признать сессию незавершённой.
Директория: `project/sessions/YYYY-MM-DD_kebab-topic/`
1. `session.md` — по формату `.claude/templates/project/session-template.md`
2. `handoff.md` — по формату `.claude/templates/project/handoff-template.md`
3. Обнови `project/sessions/index.yaml`
4. Обнови `project/ledger.md` (last_updated, фаза, задачи, артефакты, DEC) — включая секцию **«Зачем»**: миссия / цель фазы / ближайший шаг. Одна строка на уровень; события идут в `session.md`, не сюда.
5. Прогони `bash .claude/hooks/check-session-reflection.sh` — слоты раздела «Смыслы» в записанной сессии не должны остаться пустыми. Нечего сказать по слоту — так и напиши («не обнаружены»): пустой слот неотличим от пропущенного шага.

## Шаг 8: Git sync
1. `git add -A` → `git status` → проверь `git diff --cached` (нет секретов, бинарных файлов)
2. `git commit -m "session: {session_id}"`
3. Если remote настроен: `git pull --rebase origin main` → конфликт → СТОП, показать файлы. Нет конфликтов → `git push`
