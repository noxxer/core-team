# Upgrade — обновление копии Core Team

Обновляет инструмент (`.claude/`) до текущей поставки, не трогая память проекта (`project/`).
Делает это скрипт `hooks/upgrade.sh`; твоя работа — показать человеку, что изменится, получить
подтверждение и прочитать доклад. **Ничего не накладывается без явного «да».**

Зачем скрипт, а не инструкция: `UPGRADING.md` дорос до 47 заголовков, и версионные шаги копились
от релиза к релизу. Замер: 11 установок из 17 не обновлялись ни разу, переход на 5.0 был сделан
пересозданием проектов. Теперь шаги живут в `hooks/migrations/<версия>.sh`, а инструкция —
доклад о том, что изменилось в контракте.

## Шаг 1. Предпросмотр — обязателен, ничего не трогает

```bash
bash .claude/hooks/upgrade.sh
```

Скрипт берёт поставку с GitHub (старший стабильный тег) и печатает пять колонок: **приедет
сверху** · **обновится** · **ваше и останется** · **ваша правка будет перезаписана** · **убрано
у вас — не возвращается**, плюс **вопросы** — файлы, чьё происхождение он установить не смог.
Ниже — миграции с пометками БУДЕТ / УЖЕ / ВРУЧНУЮ.

Сеть недоступна — попроси человека скачать поставку и передай каталог: `--source /путь/к/core-team`.
Нужна конкретная версия — `--ref v5.4.0`.

**Что покажи человеку своими словами, не пересказывая список:**
- сколько файлов обновится и что из этого его правки (колонка «перезаписана» — назови каждый файл:
  вернуть можно из git, но знать надо до, а не после);
- что помечено ВРУЧНУЮ в миграциях — это его работа после обновления;
- вопросы — файлы, про которые скрипт не знает, чьи они: пусть решит сам.

Скрипт откажется работать на `main`/`master` и при незакоммиченном внутри `.claude/` — в этом
случае сначала `git switch -c update-core-team` и коммит, потом снова Шаг 1.

## Шаг 2. Подтверждение — `AskUserQuestion`

Один вопрос: применить обновление `X → Y` с перечисленными последствиями? Варианты: применить ·
сначала сохранить перезаписываемые правки в `upgrade.keep` · не сейчас. Без ответа — стоп.

Если человек хочет сохранить свою правку файла поставки — добавь путь в `.claude/settings.json`:

```json
"upgrade": { "keep": ["hooks/session-start.sh"] }
```

и повтори Шаг 1: файл перейдёт в колонку «ваше и останется».

## Шаг 3. Применение

```bash
bash .claude/hooks/upgrade.sh --apply            # плюс те же --source / --ref, что в Шаге 1
```

Скрипт накладывает поставку, сохраняя своё; берёт `CLAUDE.md` из поставки с вашим разделом
«Текущий проект»; сливает `settings.json` (`hooks` и `env` сверху, остальное ваше); удаляет
остатки прежних версий, которые вы не правили; исполняет миграции; прогоняет целостность копии.
**Красная целостность — откат `.claude/` целиком и код 1**: копия остаётся прежней, доложи причину.

## Шаг 4. Доклад человеку — обязателен

Из вывода скрипта передай:
1. **Что изменилось в контракте** — заголовки записей CHANGELOG за пройденные версии, своими словами:
   какие правила появились, какие приборы покраснеют впервые.
2. **ВРУЧНУЮ** — список того, что скрипт сделать не мог (права машины, строки в таблицах проекта).
3. **Закрыто из вашего `framework-feedback.md`** — если скрипт нашёл совпадения, предложи отметить
   исход в таблице «Отправлено наверх».
4. **Сводка находок проекта** после обновления — что покраснело нового. Унаследованное называй
   унаследованным, а не срочным.
5. Напоминание: плагины (`core-team-dev`, `smotrovaya`, `product-loop`) обновляются отдельно —
   `claude plugin update <имя>@core-team`.

## Шаг 5. Коммит — по подтверждению

Одной строкой, как печатает скрипт:

```bash
git commit -am "chore: обновление Core Team X → Y"
```

Слияние ветки в основную — за человеком. **Не коммить без его слова** и никогда не добавляй
`Co-Authored-By`.

## Чего не делать

- Не запускать `--apply` без Шага 1 и Шага 2 в этой же сессии.
- Не править `project/` — обновление его не касается; находки сводки разбираются в обычной сессии.
- Не «доводить» вручную то, что скрипт пометил вопросом: это решение человека.
- Не обновлять плагины этим скриптом — у них свой механизм.
