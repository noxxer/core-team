# Обновление Core Team в рабочем проекте

> **Кому адресовано.** Этому файлу следует **ИИ-агент** (Claude Code), работающий в проекте,
> где Core Team уже развёрнут. Человек может просто дать агенту ссылку на этот файл и сказать
> «обнови фреймворк по инструкции».
>
> **Что здесь есть, а чего нет.** Здесь порядок шагов, проверка после каждого и условия
> остановки. Здесь **нет** разрешения трогать `project/` — это память проекта, и она не
> обновляется вместе с инструментом.

## Инвариант всей процедуры

**`.claude/` — инструмент, он обновляется. `project/` — память, она не трогается.**
Любой шаг, который меняет что-то внутри `project/`, требует отдельного подтверждения человека.
Исключение одно: заведение отсутствующих файлов, о которых явно попросит проверка целостности,
и то — после доклада.

## Шаг 0. Ориентация — что обновляем и с чего

```bash
cat .claude/VERSION 2>/dev/null || echo "версии нет — копия старше 5.1.0"
```

Файла нет — это нормально для копий до 5.1.0: до неё `VERSION` лежал в корне репозитория
фреймворка и до потребителя не доезжал. Запиши, что нашёл: это будет точкой отсчёта в отчёте.

**Какие шаги проходить — по точке отсчёта.** Шаги 0–8 и 9–10 обязательны всегда; версионные
шаги добавляются накопительно, от старого к новому:

| Что нашёл в `.claude/VERSION` | Версионные шаги |
|---|---|
| файла нет, либо 5.0.x и старше | **8b → 8c → 8d → 8e** — весь путь |
| 5.1.x | **8c → 8d → 8e** |
| 5.2.x | **8d → 8e** |
| 5.3.0 | **8e** |

Копия старше 5.1 узнаётся ещё и по составу: в ней лежит `.claude/hooks/hooks.json` (файл,
который Claude Code не читает) и один-два проверщика вместо двадцати семи. Замер на четырёх
боевых проектах: `hooks.json` есть во всех, приборов — по одному-два.

**Остановись и спроси человека, если:** в рабочем дереве есть незакоммиченные изменения.
Обновление перезаписывает `.claude/` целиком, и потерянную правку восстановить будет нечем.

## Шаг 1. Отдельная ветка

```bash
git switch -c update-core-team
```

Обновление должно быть откатываемым одной командой: `git switch main && git branch -D update-core-team`.

## Шаг 2. Сохрани СВОИ файлы внутри `.claude/` — их два

```bash
cp .claude/settings.json          settings.json.мой
cp .claude/planner-context.md     planner-context.md.мой   # если есть
```

**`settings.json`** — `/setup-project` (Шаг 5) кладёт туда ключи под конкретный проект:
`outputStyle`, `language`, `permissions.deny`. Копирование фреймворка затрёт их **гарантированно**.

**`planner-context.md`** — накопленное обучение планировщика: пробелы, сильные стороны моделей,
поправки пользователя, калибровка цены. Он лежит в `.claude/`, хотя по раскладке это **память,
а не инструмент**, и потому переживает обычное наложение (`cp -r`), но исчезает при «чистой»
установке через `rm -rf .claude`. Замер: 118 / 556 / 97 / 124 строки в четырёх проектах — от
двух до девяти месяцев накопления.

> **Известное противоречие, названное вслух.** README объявляет: «один `.claude/` (инструмент)
> и один `project/` (память)». `planner-context.md` нарушает это правило — он память в каталоге
> инструмента. Переезд в `project/` — ломающее изменение для существующих копий (путь назван
> в навыке `planner` и в `/setup-project`), поэтому он отложен и здесь записан, а не забыт.

## Шаг 3. Забери свежую версию и посмотри, что изменится

```bash
git clone --depth 1 https://github.com/noxxer/core-team.git
rm -rf core-team/.git
diff -rq .claude core-team/.claude | head -40
```

Прочитай `core-team/CHANGELOG.md` — раздел последней версии, части «Что вы заметите» и «Что
нужно сделать при обновлении». Там перечислено то, чего нет в дифе: изменения контракта.

## Шаг 4. Перенеси инструмент

```bash
cp -r core-team/.claude .
```

**Наложение НИКОГДА не удаляет.** Файл, убранный из фреймворка, остаётся у тебя навсегда —
и продолжает выглядеть частью инструмента. Замер: проба обновления живой копии 5.1.1 → 5.2.0
оставила `hooks/verify-task.sh`, удалённый ещё в 5.1, и проверка целостности честно нашла его
как прибор без объявленного тира. Вместе с ним остались бы три шаблона, удалённые в 5.2.

Сравни, пока клон ещё на месте, и убери лишнее:

```bash
diff <(ls .claude/hooks) <(ls core-team/.claude/hooks)                 # лишние приборы
diff <(ls .claude/templates/project) <(ls core-team/.claude/templates/project)   # лишние шаблоны

rm -f .claude/hooks/verify-task.sh                                     # удалён в 5.1
rm -f .claude/templates/project/scorecard-template.md \
      .claude/templates/project/experiment-board-template.md \
      .claude/templates/project/assumptions-template.md                # удалены в 5.2
rm -rf core-team
```

> Твои `project/**` эти команды не трогают: удаляются только файлы инструмента.

## Шаг 5. Верни свои ключи

Открой `settings.json.мой` и перенеси из него в новый `.claude/settings.json` ключи проекта
(`outputStyle`, `language`, `permissions`), **сохранив пришедшие сверху `hooks` и `env`** —
в них может появиться новое событие, и потерять его значит остаться без гарда.

```bash
rm settings.json.мой   # только после того, как ключи перенесены
```

## Шаг 6. Механическая проверка — она назовёт всё поимённо

```bash
bash .claude/hooks/check-install-integrity.sh
```

Проверка отвечает на вопрос «копия **работоспособна**?», а не «файлы на месте?». Каждая находка
названа отдельной строкой. Типовые и что с ними делать:

| Находка | Что делать |
|---------|------------|
| нет `.claude/VERSION` | копирование прошло не полностью — повтори Шаг 4 |
| хук не исполняем | `chmod +x .claude/hooks/*.sh` |
| хук объявлен, файла нет | в `settings.json` остался хук из старой версии — убери объявление |
| в `settings.json` нет ни одного хука | ты потерял `hooks` на Шаге 5 — верни из свежей копии |
| роль не называет свой DPF / ремесла нет | см. Шаг 7 |
| правило ведёт в несуществующий файл | копирование неполное — повтори Шаг 4 |

**Не переходи дальше, пока строка не станет «Расхождений: 0».**

## Шаг 7. Учебники ремесла (DPF), если их нет

Копии старше 5.0 не имеют слоя DPF вовсе, и обновление `.claude/` его **не заводит**: он
генерируется под область проекта. Признак — проверка на Шаге 6 говорит «слоя DPF нет вовсе»
или «роль не называет свой DPF».

Доложи человеку и предложи: `/setup-project` (Шаг 4b) для генерации под область проекта, либо
`/self-service` implant для отдельной роли. **Сам не запускай** — это меняет `.claude/knowledge/`
и требует решений о предметной области.

## Шаг 8. Реестр дрейфа, если он ведётся

Есть `project/artifacts/drift-registry.md` — у него должно быть поле `ceiling:` в шапке
(объявленная ёмкость). Без него проверка потолка откажется работать.

Это правка внутри `project/` — **спроси человека**, какую ёмкость объявить, и назови текущее
число открытых записей, чтобы вопрос был предметным.

## Шаг 8b. Три артефакта, которых больше нет (переход на 5.2)

Фреймворк перестал возить `scorecard.md`, `experiment-board.md` и `assumptions.md`, а роль
`cto` — `tech-radar.md`. **Твои файлы никуда не денутся** — обновление их не трогает. Но
шаблонов под них больше нет, и роли на них не ссылаются. Куда переезжает содержимое:

| Файл | Куда | Почему |
|---|---|---|
| `artifacts/scorecard.md` | ниоткуда не нужен — `bash .claude/hooks/check-decision-decay.sh` обходит `decisions/` | таблица пересказывала поля `kill_criteria`, `metric_for_revisit`, `review_due`, уже лежащие в самих решениях |
| `artifacts/assumptions.md` | раздел «На чём стоит» в `DEC-NNN.md`; допущение без решения — в `backlog.md` | у допущения в решении есть читатель и дата пересмотра |
| `artifacts/experiment-board.md` | те же поля решения: гипотеза в «На чём стоит», порог в `kill_criteria`, срок в `review_due` | эксперимент — способ проверить допущение, а не отдельная сущность |
| `artifacts/tech-radar.md` | перечень колец внутри решения о стеке | второе описание всегда отстаёт от первого |

Что сделать: **прогнать `bash .claude/hooks/check-decision-decay.sh`** и разнести по решениям
то, что в этих файлах ещё живо. Остальное — удалить или увезти в архив. Унаследованные решения
(принятые до даты введения правила) прогон не роняют: они заполняются при первом касании.

Замер, ради которого: `scorecard` был заведён в 2 проектах из 4 и устарел на 30 и 98 дней,
`assumptions` и `experiment-board` — в 1 из 4, простояли 57 дней и не были открыты ни разу.
При этом в самих решениях 32 из 177 просрочили проверку релевантности, 85 не имели её вовсе,
45 назвали порог отмены и не назвали метрику.

## Шаг 8c. Новые приборы 5.2 — что покраснеет и что с этим делать

С 5.2 приезжают восемь новых проверок. **Все они введены вперёд**: унаследованное они
перечисляют и прогон не роняют. Но форму файлов проверяют сразу — и вот тут копия покраснеет,
если её не подготовить. Замер на четырёх боевых проектах: краснеет **каждый**, по 1–4 находки
на прибор.

Прогони всё разом и иди по таблице:

```bash
for g in ledger role-memory decisions decision-decay artifacts assets requirements \
         registry-ceiling drift-closure install-integrity; do
  echo "== $g"; bash .claude/hooks/check-$g.sh || true
done
```

| Что скажет | Почему | Что сделать |
|---|---|---|
| `ЛЕСТНИЦЫ СМЫСЛОВ НЕТ` | секция «Зачем» приехала в 5.1, а обновление чужой `ledger.md` не переписывает — её нет **ни в одном** из четырёх замеренных проектов | завести три строки: Миссия / Цель фазы / Ближайший шаг |
| `ПОЛЕ ПРЕВРАТИЛОСЬ В ХРОНИКУ` | пересказ сессии в поле шапки — замер: `active_phase` 4141 символ | одну строку оставить здесь, остальное в `project/sessions/` |
| `ХРОНИКА НАКАПЛИВАЕТСЯ ПОЛЯМИ` | `previous_phase_171`, `previous_phase_170` — лента без дна | убрать поля, прошлые фазы живут в сессиях |
| `ПОТОЛОК ПРОБИТ` у ledger | нет `max_lines:` в шапке (умолчание 300) | свернуть разделы состояния либо поднять `max_lines:` с причиной |
| `ПАМЯТЬ НЕ ЧИТАЕТСЯ` | файл роли выше 256 КБ — `Read` на нём отказывает молча | разобрать через `Bash` (`sed -n`, `awk`): хронику в `sessions/`, в память срез |
| `нет раздела «Активы»` | `resources.md` до 5.2 был «внешними источниками» | взять форму из `templates/project/resources.md`; активов нет — файл можно удалить |
| `У ЭТИХ ЕСТЬ ХОЗЯИН` | файлы с `FEAT`/`DEC`/`DR` в имени лежат в `artifacts/` | перенести к хозяину; замер: каждый третий файл не у себя дома |
| `нет числового поля ceiling` | реестр дрейфа старше 5.1 | добавить `ceiling:` и `enforced_since_id:` в шапку |
| `ИСТОЧНИК НЕ НАЗВАН` | у реестра дрейфа нет колонки «Источник» | добавить колонку в обе таблицы; заполнять при заведении записи |
| `НЕТ ДАТЫ ПРИНЯТИЯ` / `НЕТ ДАТЫ ПРОВЕРКИ` | у решения нет `date_proposed` или `review_due` | заполнить; замер: 85 решений из 177 без даты проверки |
| `Не взяты (N из M)` | требования без исполнителя — норма до ёмкости | назвать исполнителя либо поднять `unassigned_ceiling:` |

**Порядок, который экономит время.** Сначала `check-drift-closure.sh` — он печатает **очередь
разблокировки**: какое решение освобождает больше всего записей. Потом ledger и память ролей —
они самые дешёвые. Реестры и артефакты последними: там работа объёмная, и её видно заранее.

**Ничего не удаляется автоматически.** Все проверки только читают; ни одна не правит файлы.

## Шаг 8d. Переход на 5.3 — ремесло уехало в плагины

Это самый крупный шаг обновления и единственный, после которого копия **работает иначе**,
а не просто строже. Три вещи меняются сразу: часть инструмента уезжает из `.claude/`,
появляется таблица подключений, и хуки переезжают в другой файл.

### 8d.1. Четыре команды и пять навыков исчезнут из копии

Ремесло разработки больше не входит в ядро. После наложения новой версии в
`.claude/commands/` **не будет**:

```
plan-feat.md   plan.md   plan-do.md   plan-reflect.md
```

и в `.claude/skills/` не будет `tdd-master`, `functional-clarity`, `planner`,
`planner-reflect`, `stacks`. Они приезжают плагином `core-team-dev`.

Проверь, чем ты пользуешься на самом деле:

```bash
grep -rl 'plan-feat\|/plan-do\|tdd-master\|planner' project/sessions/ 2>/dev/null | wc -l
```

**Пользуешься — поставь плагин** (иначе четыре команды просто перестанут существовать,
и узнаешь ты об этом в момент вызова):

```bash
claude plugin marketplace add noxxer/core-team
claude plugin install core-team-dev@core-team --scope project
claude plugin list                     # Status обязан быть enabled, а не просто installed
```

**Не пользуешься — не ставь.** Ядро без плагина работает; роли переходят на общие принципы
и **говорят об этом вслух**, а не молчат. Именно ради этого «вслух» и заведён следующий пункт.

> **`planner-context.md` остаётся на месте.** Навык `planner` уехал, его память — нет:
> файл лежит в `.claude/planner-context.md`, обновление его не трогает (Шаг 2), проверка
> ссылок про него знает. Без плагина он просто никем не читается — не удаляй его, пока не
> решишь, что планировщик больше не нужен.

### 8d.2. Заведи таблицу подключений — без неё роли считают инструменты установленными

Появилось правило: **инструмент подключается точкой, а не догадкой.** Ядро объявляет слои
работы, проект объявляет, чем каждый закрыт. Незакрытый слой обязан назвать деградацию —
как работаем без инструмента и что перестаёт считаться.

```bash
cp .claude/templates/project/connection-points.md project/connection-points.md
```

Это правка внутри `project/` — **скажи человеку, что заводишь файл, и покажи заполненную
таблицу**. Заполняется она так:

| Колонка | Что писать |
|---|---|
| **Чем закрыта** | имя плагина (`core-team-dev`), слово `ядро`, слово `неприменимо` или прочерк |
| **Где лежит** | путь к результату слоя — **обязателен**, если слой ведёт инструмент со стороны |
| **Деградация** | обязательна при прочерке и при `неприменимо`: как работаем без инструмента |

Шаблон приезжает с уже заполненными деградациями — если плагинов нет, менять в нём почти
нечего. Три случая, ради которых стоит вчитаться:

- **Плагин стоит, но выключен.** «Установлен» не отвечает на вопрос «работает»: роль зовёт
  навык, которого в сессии нет, и молча продолжает без него. Замер: шесть плагинов
  `i-m-senior-developer` стоят установленными и выключенными.
- **Слой ведёт чужой инструмент.** Назови адрес результата, иначе проверки ядра пойдут по
  своему пути и скажут «ноль» при восьми записях — так и случилось на боевом прогоне
  с требованиями.
- **Слоя не может быть в принципе.** Проект-исследование, организационный, образовательный
  пишет `неприменимо` и причину: «проект не пишет код». Строку **не удаляй** — слой, о
  котором проект не сказал ничего, невидим.

Проверка:

```bash
bash .claude/hooks/check-connection-points.sh
```

### 8d.3. Хуки переехали в `settings.json` — у тебя они, скорее всего, не работали

Claude Code читает хуки **только** из `.claude/settings.json`. Файл `.claude/hooks/hooks.json`
не читается никогда — он остался от старой раскладки и удалён в 5.1.

```bash
ls .claude/hooks/hooks.json 2>/dev/null && echo "есть — он мёртвый, удалить"
python3 -c "import json;print(list(json.load(open('.claude/settings.json')).get('hooks',{})))"
```

В 5.3 событий три: `SessionStart` (старт сессии), `SubagentStop` (роль вернулась с работы),
`PreToolUse` (правка памяти и запись сессии). Замер на четырёх боевых проектах: `hooks.json`
лежит во всех трёх проверенных, а в `settings.json` объявлен `SessionStart` только у двух —
у остальных стартовый хук не срабатывал вовсе, и протокол в сессию не инжектировался.

Свежий `settings.json` из новой копии объявляет все три. Если ты сохранял свой файл на Шаге 2,
верни из него **только** `outputStyle`, `language` и `permissions` — блок `hooks` бери из
новой версии целиком.

> **Про `TaskCompleted` и `verify-task.sh`.** Во всех четырёх замеренных копиях объявлено
> событие `TaskCompleted` с хуком `verify-task.sh`. Событие существует, но фреймворк от него
> отказался по замеру: **ноль срабатываний на 143 закрытия задач** — его вход не совпадал
> с тем, что хук ждал (`knowledge/guide-multi-agent-teams.md`). Если вернуть свой блок
> `hooks` целиком, мёртвое объявление переедет в новую копию и будет выглядеть работающим.
> Удали и объявление, и сам `verify-task.sh`: его работу — проверку того, что роль вернулась
> с результатом, — делает `SubagentStop` через `subagent-arrival.sh`.

### 8d.4. Новые артефакты — заводятся по мере надобности, кроме одного

| Файл | Когда нужен | Что будет без него |
|---|---|---|
| `connection-points.md` | **всегда** (8d.2) | роли считают инструменты подключёнными; проверка молчит |
| `requirements.md` | есть обязательства с номерами | требования живут прозой в решениях и теряются |
| `claims.md` | есть ставки о мире, у которых **есть дети** | утверждения смешаны с фактами в `domain.md` |
| `design-system.md` | у продукта есть интерфейс | облик нигде не записан, фронт делается «как получится» |
| `work/` | ведёшь ленты работ | задачи живут в `backlog.md`, как раньше |

Признак для `claims.md` жёсткий: **у утверждения есть дети** — на него ссылается паспорт или
сценарии. Нет детей — запись остаётся фактом в `domain.md`. Не переноси всё подряд.

### 8d.5. Что покраснеет на приборах 5.3

Приезжают пять новых проверок: заполненность (`check-filled`), точки подключения
(`check-connection-points`), след работы (`check-work-trail`), связность ссылок
(`check-links`) и витрина плагинов (`check-marketplace` — только для репозитория-маркета,
у потребителя молчит). Прогони всё одной командой — **сводка принимает корень проекта
аргументом**, так что её можно позвать откуда угодно:

```bash
bash .claude/hooks/check-findings-budget.sh /путь/к/проекту
```

Она делит находки на **стоп** (разбирается сейчас) и **счёт** (копится под потолком) и сама
задаёт порядок: дешёвое из дорогого первым. Что увидишь чаще всего:

| Что скажет | Почему | Что сделать |
|---|---|---|
| `остался шаблоном — подсказок не заполнено` | `check-filled.sh`: артефакт скопирован и не тронут. Прежние приборы умели говорить «этого слишком много» и молчали, когда содержания нет вовсе | заполнить либо удалить файл, если он не нужен |
| `точка канона в проекте отсутствует` | таблица подключений не заведена или неполна | вернуться к 8d.2 |
| `АДРЕС ВЕДЁТ В НИКУДА` | требование заявляет покрытие файлом, которого нет | завести файл либо описать проверку словами — описание путём не считается |
| `код есть, а зачем он построен нигде не записано` | `check-work-trail.sh`: ни замысла, ни описания продукта | завести любой из двух законных входов; проект без кода прибор не трогает |
| `ссылка ведёт в несуществующий файл` | `check-links.sh`: пути внутри `.claude/` после переименований | чинить в порядке появления; путей в `project/` прибор не проверяет |

**Все приборы введены вперёд:** унаследованное они перечисляют и прогон не роняют. Сессия,
записанная до 2026-08-26, слотов смыслов содержать не могла — она называется в отчёте и
прогон не валит. Решения старше 2026-08-25 заполняются при первом касании.

### 8d.7. Что называть человеку в докладе по этому шагу

1. **Поставлен ли плагин ремесла** — и если нет, какие четыре команды перестали существовать.
2. **Заполненная таблица подключений** целиком: она отвечает на вопрос «чем мы вообще
   работаем», и человек должен увидеть её один раз своими глазами.
3. **Работали ли хуки раньше** — по факту содержимого `settings.json` до обновления.
   Ответ «не работали» встречается чаще, чем кажется, и объясняет, почему протокол
   не появлялся в сессиях.

## Шаг 8e. Переход на 5.3.1 — границы и починки первого прогона

Версия патчевая: один новый артефакт и восемь починок, найденных на первом прогоне
чистой копии и на боевом проекте. Пункт 8e.1 **обязателен** — без него гард точек подключения
покраснеет; остальные выполняются по состоянию копии.

### 8e.1. Точка `boundary-contract` в таблице подключений — обязательно

В канон добавлена точка `boundary-contract`. Прибор требует, чтобы **каждая точка канона**
присутствовала в проектной таблице: слой, о котором проект не сказал ничего, невидим.
Допиши строку в `project/connection-points.md`:

```
| `boundary-contract` | границы между контурами перечислены: у каждой один источник формы и адрес сверки либо долг с датой | ядро | ядро | `boundaries.md` | — |
```

Проекту без кода — `неприменимо` в колонке «Чем закрыта» и причина в «Деградации».

Проверка: `bash .claude/hooks/check-connection-points.sh`.

### 8e.2. Реестр границ — если контуров больше одного

Новый артефакт `project/boundaries.md` (шаблон — `.claude/templates/project/boundaries.md`).
Заводится, когда у продукта есть хотя бы две стороны, обменивающиеся данными: фронт и бек,
внешний сервис, очередь, набор алертов, тестовый стенд.

Единица — **пара сторон, а не вызов**. Границ обычно пять-шесть; если получается больше
десяти, скорее всего перечисляются ручки, а не границы.

У каждой границы — либо адрес гарда, либо долг: `принято как долг до ГГГГ-ММ-ДД, владелец <роль>`.
Первый прогон почти наверняка даст красное на всех границах разом: это нормально, разбирается
по одной, и то, что не чинится сегодня, объявляется долгом с датой.

Проверка: `bash .claude/hooks/check-boundaries.sh`.

### 8e.3. Блок «Для памяти роли» в опциональных ролях — если они подключены

Замер прогона 5.3.0: блок был описан у 6 ядровых ролей из 6 и у **0 опциональных из 5**
(`product`, `guardian`, `analyst`, `designer`, `customer`). Хук `subagent-arrival.sh`
требует этот раздел в отчёте любой роли, у которой есть файл в `.claude/agents/`, — значит
любая opt-in роль вставала на первой же активации, и причина из её файла не была видна.

Обновление `.claude/` привозит починенные шаблоны. Но если opt-in роль **уже скопирована**
в `.claude/agents/` в вашей копии, файл там — ваш, и обновление его не трогает:

```bash
grep -c '^## Для памяти роли' .claude/agents/*.md
```

Ноль у любой роли, кроме `facilitator`, — скопируйте блок из
`.claude/templates/roles/optional/product.md` (или из любой ядровой роли) в конец файла.

Проверка: `bash .claude/hooks/check-install-integrity.sh` — теперь ловит и ноль описаний,
а не только дубль.

### 8e.4. Плагины: проверьте, что они включены, а не только установлены

Замер того же прогона: после `claude plugin install` все три плагина `core-team` показали
`Status: ✘ disabled`. Установка **не включает** плагин, и точки, которые он закрывает,
остаются открытыми — роли работают без ремесла молча.

```bash
claude plugin list
claude plugin enable <плагин>@<маркетплейс> --scope project   # для каждого выключенного
```

Правило и гард существовали с 5.3; отставала инструкция, по которой действует человек, —
в 5.3.1 команда `enable` добавлена и в `/setup-project`, и в шаблон таблицы подключений.

### 8e.5. Память ролей: проверьте размер, если прыгаете со старых версий

```bash
bash .claude/hooks/check-role-memory.sh
```

Копии старше 5.2 этого прибора не имели вовсе. Замер боевого проекта на 2026-08-31: у роли
`dev` память 461 КБ, у `architect` — 296 КБ при **пределе чтения 256 КБ**. Роль за этим
порогом не падает — она молча работает без накопленного; в том проекте так прошло десять дней,
и заметил это человек по случайной реплике в свободном тексте отчёта.

Два предостережения при разборе:

- **резать нечем той роли, которой файл принадлежит:** `architect`, `keeper`, `test`,
  `customer`, `product` объявлены без `Bash`. Разбирает `facilitator` или `keeper`;
- **рез по дате бывает опасен:** в том же проекте один файл содержал два журнала с разным
  направлением, а под разделами шаблона лежало 41 КБ действующих правил. Проверьте направление
  записи прежде, чем отрезать хвост.

### 8e.6. Мелочи, которые обновление привозит само

Правятся файлы фреймворка, от вас действий не требуется: законная форма пустоты в шаблоне
`domain.md` (первый день проекта, когда фактов ещё нет), раздел «Ценности этого проекта»
в шаблоне ценностей, условность Шага 6 и перенос Шага 7 в `/setup-project`, строка
«Память роли: прочитана / НЕ ПРОЧИТАНА» в форме отчёта роли.

## Шаг 10. Доклад человеку — обязательный

Не объявляй обновление законченным без этого. В докладе:

1. **С какой версии на какую** обновились.
2. **Что изменилось в контракте** — из раздела «Что вы заметите» changelog-а: что поменяется в
   поведении ролей и сессий. Не пересказывай весь changelog, назови то, что коснётся этого проекта.
3. **Что проверка нашла и как это закрыто** — построчно.
4. **Что осталось за человеком:** генерация DPF, ёмкость реестра, решения, упомянутые в ledger
   без файла (обоснование там уже потеряно — их придётся либо восстановить, либо убрать
   упоминание).
5. **Если проходил Шаг 8d** — три его пункта отдельно: поставлен ли плагин ремесла и какие
   команды исчезли без него; заполненная таблица подключений целиком; работали ли хуки до
   обновления. Последнее часто оказывается «не работали» и объясняет, почему протокол
   не появлялся в сессиях.
5. **Как откатиться:** `git switch main && git branch -D update-core-team`.

## Условия остановки — когда не продолжать, а спрашивать

- В рабочем дереве были незакоммиченные изменения.
- Проверка целостности не сходится к нулю после двух попыток.
- Diff показывает, что твои собственные правки внутри `.claude/` будут потеряны, и ты не знаешь,
  нужны ли они.
- Обновление требует изменить что-либо в `project/` сверх перечисленного здесь.
- Версия в `.claude/VERSION` после обновления не совпала с той, что в changelog свежей копии.

## Чего не делать

- **Не трогать `project/`** без явного подтверждения — там память проекта, а не инструмент.
- **Не «чинить» унаследованные артефакты автоматически.** Сессии и решения, записанные по старым
  шаблонам, считаются унаследованными: новые проверки их не роняют. Массовая переделка задним
  числом уничтожает свидетельство того, как проект шёл.
- **Не вести проект внутри клона фреймворка.** Клон — источник, твой проект — отдельный
  репозиторий (подробнее — в README).
