# Обновление Core Team в рабочем проекте

> **Кому адресовано.** Этому файлу следует **ИИ-агент** (Claude Code), работающий в проекте,
> где Core Team уже развёрнут. Человек может просто дать агенту ссылку на этот файл и сказать
> «обнови фреймворк по инструкции».
>
> **Что здесь есть, а чего нет.** Здесь порядок шагов, проверка после каждого и условия
> остановки. Здесь **нет** разрешения трогать `project/` — это память проекта, и она не
> обновляется вместе с инструментом.

## Инвариант всей процедуры

**`.claude/` — инструмент, он обновляется. `project/` — память, она не трогается.**
Любой шаг, который меняет что-то внутри `project/`, требует отдельного подтверждения человека.
Исключение одно: заведение отсутствующих файлов, о которых явно попросит проверка целостности,
и то — после доклада.

## Шаг 0. Ориентация — что обновляем и с чего

```bash
cat .claude/VERSION 2>/dev/null || echo "версии нет — копия старше 5.1.0"
```

Файла нет — это нормально для копий до 5.1.0: до неё `VERSION` лежал в корне репозитория
фреймворка и до потребителя не доезжал. Запиши, что нашёл: это будет точкой отсчёта в отчёте.

**Остановись и спроси человека, если:** в рабочем дереве есть незакоммиченные изменения.
Обновление перезаписывает `.claude/` целиком, и потерянную правку восстановить будет нечем.

## Шаг 1. Отдельная ветка

```bash
git switch -c update-core-team
```

Обновление должно быть откатываемым одной командой: `git switch main && git branch -D update-core-team`.

## Шаг 2. Сохрани СВОИ файлы внутри `.claude/` — их два

```bash
cp .claude/settings.json          settings.json.мой
cp .claude/planner-context.md     planner-context.md.мой   # если есть
```

**`settings.json`** — `/setup-project` (Шаг 5) кладёт туда ключи под конкретный проект:
`outputStyle`, `language`, `permissions.deny`. Копирование фреймворка затрёт их **гарантированно**.

**`planner-context.md`** — накопленное обучение планировщика: пробелы, сильные стороны моделей,
поправки пользователя, калибровка цены. Он лежит в `.claude/`, хотя по раскладке это **память,
а не инструмент**, и потому переживает обычное наложение (`cp -r`), но исчезает при «чистой»
установке через `rm -rf .claude`. Замер: 118 / 556 / 97 / 124 строки в четырёх проектах — от
двух до девяти месяцев накопления.

> **Известное противоречие, названное вслух.** README объявляет: «один `.claude/` (инструмент)
> и один `project/` (память)». `planner-context.md` нарушает это правило — он память в каталоге
> инструмента. Переезд в `project/` — ломающее изменение для существующих копий (путь назван
> в навыке `planner` и в `/setup-project`), поэтому он отложен и здесь записан, а не забыт.

## Шаг 3. Забери свежую версию и посмотри, что изменится

```bash
git clone --depth 1 https://github.com/noxxer/core-team.git
rm -rf core-team/.git
diff -rq .claude core-team/.claude | head -40
```

Прочитай `core-team/CHANGELOG.md` — раздел последней версии, части «Что вы заметите» и «Что
нужно сделать при обновлении». Там перечислено то, чего нет в дифе: изменения контракта.

## Шаг 4. Перенеси инструмент

```bash
cp -r core-team/.claude .
rm -rf core-team
```

## Шаг 5. Верни свои ключи

Открой `settings.json.мой` и перенеси из него в новый `.claude/settings.json` ключи проекта
(`outputStyle`, `language`, `permissions`), **сохранив пришедшие сверху `hooks` и `env`** —
в них может появиться новое событие, и потерять его значит остаться без гарда.

```bash
rm settings.json.мой   # только после того, как ключи перенесены
```

## Шаг 6. Механическая проверка — она назовёт всё поимённо

```bash
bash .claude/hooks/check-install-integrity.sh
```

Проверка отвечает на вопрос «копия **работоспособна**?», а не «файлы на месте?». Каждая находка
названа отдельной строкой. Типовые и что с ними делать:

| Находка | Что делать |
|---------|------------|
| нет `.claude/VERSION` | копирование прошло не полностью — повтори Шаг 4 |
| хук не исполняем | `chmod +x .claude/hooks/*.sh` |
| хук объявлен, файла нет | в `settings.json` остался хук из старой версии — убери объявление |
| в `settings.json` нет ни одного хука | ты потерял `hooks` на Шаге 5 — верни из свежей копии |
| роль не называет свой DPF / ремесла нет | см. Шаг 7 |
| правило ведёт в несуществующий файл | копирование неполное — повтори Шаг 4 |

**Не переходи дальше, пока строка не станет «Расхождений: 0».**

## Шаг 7. Учебники ремесла (DPF), если их нет

Копии старше 5.0 не имеют слоя DPF вовсе, и обновление `.claude/` его **не заводит**: он
генерируется под область проекта. Признак — проверка на Шаге 6 говорит «слоя DPF нет вовсе»
или «роль не называет свой DPF».

Доложи человеку и предложи: `/setup-project` (Шаг 4b) для генерации под область проекта, либо
`/self-service` implant для отдельной роли. **Сам не запускай** — это меняет `.claude/knowledge/`
и требует решений о предметной области.

## Шаг 8. Реестр дрейфа, если он ведётся

Есть `project/artifacts/drift-registry.md` — у него должно быть поле `ceiling:` в шапке
(объявленная ёмкость). Без него проверка потолка откажется работать.

Это правка внутри `project/` — **спроси человека**, какую ёмкость объявить, и назови текущее
число открытых записей, чтобы вопрос был предметным.

## Шаг 8b. Три артефакта, которых больше нет (переход на 5.2)

Фреймворк перестал возить `scorecard.md`, `experiment-board.md` и `assumptions.md`, а роль
`cto` — `tech-radar.md`. **Твои файлы никуда не денутся** — обновление их не трогает. Но
шаблонов под них больше нет, и роли на них не ссылаются. Куда переезжает содержимое:

| Файл | Куда | Почему |
|---|---|---|
| `artifacts/scorecard.md` | ниоткуда не нужен — `bash .claude/hooks/check-decision-decay.sh` обходит `decisions/` | таблица пересказывала поля `kill_criteria`, `metric_for_revisit`, `review_due`, уже лежащие в самих решениях |
| `artifacts/assumptions.md` | раздел «На чём стоит» в `DEC-NNN.md`; допущение без решения — в `backlog.md` | у допущения в решении есть читатель и дата пересмотра |
| `artifacts/experiment-board.md` | те же поля решения: гипотеза в «На чём стоит», порог в `kill_criteria`, срок в `review_due` | эксперимент — способ проверить допущение, а не отдельная сущность |
| `artifacts/tech-radar.md` | перечень колец внутри решения о стеке | второе описание всегда отстаёт от первого |

Что сделать: **прогнать `bash .claude/hooks/check-decision-decay.sh`** и разнести по решениям
то, что в этих файлах ещё живо. Остальное — удалить или увезти в архив. Унаследованные решения
(принятые до даты введения правила) прогон не роняют: они заполняются при первом касании.

Замер, ради которого: `scorecard` был заведён в 2 проектах из 4 и устарел на 30 и 98 дней,
`assumptions` и `experiment-board` — в 1 из 4, простояли 57 дней и не были открыты ни разу.
При этом в самих решениях 32 из 177 просрочили проверку релевантности, 85 не имели её вовсе,
45 назвали порог отмены и не назвали метрику.

## Шаг 8c. Новые приборы 5.2 — что покраснеет и что с этим делать

С 5.2 приезжают восемь новых проверок. **Все они введены вперёд**: унаследованное они
перечисляют и прогон не роняют. Но форму файлов проверяют сразу — и вот тут копия покраснеет,
если её не подготовить. Замер на четырёх боевых проектах: краснеет **каждый**, по 1–4 находки
на прибор.

Прогони всё разом и иди по таблице:

```bash
for g in ledger role-memory decisions decision-decay artifacts assets requirements \
         registry-ceiling drift-closure install-integrity; do
  echo "== $g"; bash .claude/hooks/check-$g.sh || true
done
```

| Что скажет | Почему | Что сделать |
|---|---|---|
| `ЛЕСТНИЦЫ СМЫСЛОВ НЕТ` | секция «Зачем» приехала в 5.1, а обновление чужой `ledger.md` не переписывает — её нет **ни в одном** из четырёх замеренных проектов | завести три строки: Миссия / Цель фазы / Ближайший шаг |
| `ПОЛЕ ПРЕВРАТИЛОСЬ В ХРОНИКУ` | пересказ сессии в поле шапки — замер: `active_phase` 4141 символ | одну строку оставить здесь, остальное в `project/sessions/` |
| `ХРОНИКА НАКАПЛИВАЕТСЯ ПОЛЯМИ` | `previous_phase_171`, `previous_phase_170` — лента без дна | убрать поля, прошлые фазы живут в сессиях |
| `ПОТОЛОК ПРОБИТ` у ledger | нет `max_lines:` в шапке (умолчание 300) | свернуть разделы состояния либо поднять `max_lines:` с причиной |
| `ПАМЯТЬ НЕ ЧИТАЕТСЯ` | файл роли выше 256 КБ — `Read` на нём отказывает молча | разобрать через `Bash` (`sed -n`, `awk`): хронику в `sessions/`, в память срез |
| `нет раздела «Активы»` | `resources.md` до 5.2 был «внешними источниками» | взять форму из `templates/project/resources.md`; активов нет — файл можно удалить |
| `У ЭТИХ ЕСТЬ ХОЗЯИН` | файлы с `FEAT`/`DEC`/`DR` в имени лежат в `artifacts/` | перенести к хозяину; замер: каждый третий файл не у себя дома |
| `нет числового поля ceiling` | реестр дрейфа старше 5.1 | добавить `ceiling:` и `enforced_since_id:` в шапку |
| `ИСТОЧНИК НЕ НАЗВАН` | у реестра дрейфа нет колонки «Источник» | добавить колонку в обе таблицы; заполнять при заведении записи |
| `НЕТ ДАТЫ ПРИНЯТИЯ` / `НЕТ ДАТЫ ПРОВЕРКИ` | у решения нет `date_proposed` или `review_due` | заполнить; замер: 85 решений из 177 без даты проверки |
| `Не взяты (N из M)` | требования без исполнителя — норма до ёмкости | назвать исполнителя либо поднять `unassigned_ceiling:` |

**Порядок, который экономит время.** Сначала `check-drift-closure.sh` — он печатает **очередь
разблокировки**: какое решение освобождает больше всего записей. Потом ledger и память ролей —
они самые дешёвые. Реестры и артефакты последними: там работа объёмная, и её видно заранее.

**Ничего не удаляется автоматически.** Все проверки только читают; ни одна не правит файлы.

## Шаг 9. Аудит связности

Запусти `/self-service` в режиме аудита. Проверь: все активные роли достижимы, нет осиротевших
артефактов, File Ownership непротиворечив, нет висячих ссылок на удалённые файлы, проектные
артефакты совместимы с новой структурой.

## Шаг 10. Доклад человеку — обязательный

Не объявляй обновление законченным без этого. В докладе:

1. **С какой версии на какую** обновились.
2. **Что изменилось в контракте** — из раздела «Что вы заметите» changelog-а: что поменяется в
   поведении ролей и сессий. Не пересказывай весь changelog, назови то, что коснётся этого проекта.
3. **Что проверка нашла и как это закрыто** — построчно.
4. **Что осталось за человеком:** генерация DPF, ёмкость реестра, решения, упомянутые в ledger
   без файла (обоснование там уже потеряно — их придётся либо восстановить, либо убрать
   упоминание).
5. **Как откатиться:** `git switch main && git branch -D update-core-team`.

## Условия остановки — когда не продолжать, а спрашивать

- В рабочем дереве были незакоммиченные изменения.
- Проверка целостности не сходится к нулю после двух попыток.
- Diff показывает, что твои собственные правки внутри `.claude/` будут потеряны, и ты не знаешь,
  нужны ли они.
- Обновление требует изменить что-либо в `project/` сверх перечисленного здесь.
- Версия в `.claude/VERSION` после обновления не совпала с той, что в changelog свежей копии.

## Чего не делать

- **Не трогать `project/`** без явного подтверждения — там память проекта, а не инструмент.
- **Не «чинить» унаследованные артефакты автоматически.** Сессии и решения, записанные по старым
  шаблонам, считаются унаследованными: новые проверки их не роняют. Массовая переделка задним
  числом уничтожает свидетельство того, как проект шёл.
- **Не вести проект внутри клона фреймворка.** Клон — источник, твой проект — отдельный
  репозиторий (подробнее — в README).
